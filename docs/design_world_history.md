# 폰 기록 · 세계 역사 · 앎

**한 줄**: 폰에게 **사라져도 남는 신원**을 주고, 세계에 일어난 일은 **한 곳(`WorldHistory`)에 한 줄씩** 적는다.
누가 그 일을 아는가는 **저장하지 않고 계산한다.** 개인 호감도 사건에서 계산한다.

2026-11-16 설계. 사용자 결정: 소문 범위는 **고정** · 개인 호감과 세력 우호도는 **분리** · 목격자 **1차에 포함** ·
떠난 폰 재등장 **포함**. 나중에 붙을 것: **세력 영역 변화**(A 소굴을 부수면 B가 차지) · **퀘스트 결과가 역사로 남는 것**.

---

## 1. 왜 필요한가 — 지금 빠져 있는 것

1. **폰 단위 신원이 없다.** `UnitBrain.All`은 *살아 있는 뇌* 목록일 뿐이라 사라진 폰은 추적되지 않는다.
2. **사라질 때 남기는 것이 없다.**
   - `BandMaterializer.Dematerialize`는 살았나 죽었나만 세고 부상·소지품을 버린다.
   - 떠돌이·행상인은 떠나면(`BTNpcNodes`의 `Object.Destroy(bb.Self)`) 완전히 사라진다.
   - Persistent가 아닌 마을 사람은 청크가 다시 올라오면 **처음 상태로** 다시 선다. 죽인 사람도 다시 선다.
3. **이유가 버려진다.** `FactionRelations.Add(세력, 변화량, reason)`은 이유를 받지만 숫자만 바꾼다.
   우호도가 왜 −40인지 게임이 모른다(`WorldRansom` · `PrisonCage` · `UnitBrain` 세 곳이 부른다).
4. **게임 전체에 세이브가 없다.** 이 설계는 세이브를 만들지 않지만, **세이브가 레지스트리 두 개를 그대로 쓰는 것으로
   끝나도록** 규약을 지금부터 지킨다(10절).

---

## 2. 세 층 — 상태 · 역사 · 앎

```
① 세계 상태   지금 어떤가        소굴이 비었다 · 우호도 −60 · 그 상인은 죽었다
               게임 로직이 읽는다   WorldLairs / FactionRelations / SiteRegistry / PawnRecord.Status

② 세계 역사   무슨 일이 있었나   15일, 플레이어가 고블린 소굴을 쓸어버렸다
               NPC 대화·AI가 읽는다 WorldHistory — 사건 하나 = 한 줄, 유일한 출처

③ 앎          누가 아는가        계산한다. 저장하지 않는다
               폰의 처지(세력·고향·위치) × 사건의 범위
```

**①과 ②는 서로를 대신하지 못한다.** "소굴이 비었다"는 상태라서 무리를 더 내보내지 않는 로직이 쓰고,
"누가 언제 쓸었나"는 역사라서 NPC가 꺼내는 이야기가 쓴다. **사건이 적히는 순간 그 결과가 상태에 한 번
반영된다**(소굴 → 비어 있음, 우호도 −50). 상태를 역사에서 매번 다시 계산하지 않는다.

**③을 저장하지 않는 이유**: 마을 하나를 부수면 그 세력 사람 수십 명이 안다. 폰마다 기억으로 복사하면
같은 사실이 수십 벌이 되고, 하나만 고쳐져도 어긋난다(*답이 두 벌이면 반드시 어긋난다*).

## 3. 폰 기록 — `PawnRegistry`

### 3-1. 신원: `PawnSpec.Id` (string)

| 폰 | Id | 비고 |
|---|---|---|
| 저작된 자리에 선 폰 | `place:<저작 Id>` | `WorldContentStreamer.SpecFor`가 이미 쓰는 안정된 id. 세이브 없이도 판마다 같다 |
| 굴려서 나온 폰 | `p:<일련번호>` | 카운터는 레지스트리가 든다(세이브 대상) |

**Id를 `PawnSpec`에 두는 이유**: 생성 경로가 여럿이지만(`WorldContentStreamer.Placed` · `BandMaterializer` ·
`WildSpawner` · `EventManager` · `BandLeader` · `Necromancy`) **전부 `ApplySpec`이나 `UnitBrain.Start`를 지난다.**
신원이 명세에 실려 오면 등록은 `Start` **한 곳**에서 끝난다 — 경로마다 고치지 않는다.

### 3-2. 기록 한 장: `PawnRecord`

```
Id
Spec           태생 — 이름·등급·특성·출신·성별 (이미 있는 PawnSpec)
Body           몸 — 부상·장비·소지품·경험치            ← 실체가 없을 때만 여기가 진짜
Status         처지 — 아래 3-4
FactionId      지금 세력 (전향하면 바뀐다)
HomeSiteId     어디 사람인가 — 마을 사람은 그 마을, 무리는 소굴(WorldBand.HomeId), 떠돌이는 비움
LastPosition   마지막으로 있던 월드 좌표
CreatedDay     기록이 생긴 날
```

**사회 데이터(기억·호감)는 여기 없다** — 5절에서 역사로부터 계산한다.

### 3-3. 실체 ↔ 기록 — 몸이 진짜인 곳은 늘 하나

`BandMaterializer`의 *"멀 땐 토큰, 가까우면 실체"*와 같은 축이다.

```
UnitBrain.Start      → PawnRegistry.Attach(brain)
                        Spec.Id가 있으면 기록을 찾아 Body를 입힌다. 없으면 새 기록을 만든다.
                        Status = Live.  이때부터 Body의 진짜는 UnitBrain이다.

UnitBrain.OnDestroy  → PawnRegistry.Detach(brain, 이유)
                        Body를 기록에 다시 적는다. 이유로 Status를 정한다.

UnitBrain.BecomeCorpse → Status = Dead.  기록은 지우지 않는다.
```

- **`OnDisable`에 걸지 않는다.** 원정·비활성 정착지는 폰을 *끄기만* 한다(`SettlementManager`). 꺼진 동안에도 그 폰이 진짜다.
- **Detach의 이유는 부르는 쪽이 넘긴다** — 떠나기(`Departed`) · 청크 내림(`AtSite`) · 무리로 거둠(`InBand`).
  이유 없이 파괴되면 `AtSite`도 `Departed`도 아닌 **`Unknown`으로 적고 콘솔에 경고한다**(조용히 틀리지 않게).
- **이유를 넘기는 문은 `UnitBrain.Despawn(이유)` 하나다**(1단계 구현, 2026-11-18). `OnDestroy`는 인자를 못 받으므로
  이유를 먼저 적고 파괴한다. 부르는 곳: 청크 내림 `AtSite`(`WorldContentStreamer.Unload`) · 무리로 거둠 `InBand`
  (`BandMaterializer`) · 떠남 `Departed`(떠나기 노드 셋 `NpcLeave` · `WildSpawner.Reap` · 무리가 버린 기절자).
  판을 닫을 때 · 씬이 내려갈 때는 사건이 아니라 안 적는다. **`Dead`는 되돌리지 않는다**(시체가 치워져도 · 일으켜져도).
- 청크를 내릴 때 **이 자리 사람이 아니게 된 폰**(내 세력 · 갇힘 · 업힘)은 안 내린다 — 예전엔 영입한 마을 사람이 사라졌다.

### 3-4. 처지: `PawnStatus`

`Live` · `InBand` · `AtSite` · `Departed` · `Colonist` · `Prisoner` · `Dead` · `Unknown`

**세우는 쪽이 처지를 먼저 묻는다** — 지금 빠져 있는 것을 고치는 자리다.
- `WorldContentStreamer.Placed`: 그 id의 기록이 `Dead` · `Departed` · `Colonist` · **`Live`**면 **세우지 않는다**
  (`PawnRegistry.BlocksRespawn`). `Live`는 구현하며 더했다 — 몸이 이미 어딘가 서 있으면(데려온 마을 사람 ·
  업혀 간 포로) 다시 세운 순간 같은 사람이 둘이 된다. (예전엔 죽인 마을 사람이 청크를 다시 밟으면 다시 섰다.)
- `BandMaterializer`: `BandMember.Spec.Id`로 기록을 찾아 Body를 입힌다. 거둘 때 `TakeLosses(개수)` 대신
  **누가 빠졌는지**를 그 사람으로 센다 — 죽음 `Dead` · 기절(버리고 감) `Departed` · 내 세력 · 붙잡힘 · 업힘은 빠지고
  몸을 안 거둔다 · 남은 사람은 `InBand`.
- **아직 적는 자리가 없는 처지**: `Colonist` · `Prisoner`(지금은 `Live`로 남는다 — 다시 세우지 않는 것은 같다).
  추상 전투(`WorldBattle` → `TakeLosses`)로 빠진 멤버는 기록이 `InBand`로 남는다.

### 3-5. 기록 대상과 정리

- **`UnitData.UsesBackstory`인 폰만** 기록한다. 짐승·이름 없는 몬스터는 기록하지 않는다.
- **정리**: `Dead` · `Departed`이고 **그 폰이 `Involved`에 든 사건이 하나도 없으면** N일 뒤 지운다.
  플레이어와 얽힌 적 없는 산적까지 남길 이유가 없다. 사건에 이름이 남은 폰은 지우지 않는다
  (지우면 "그 사람"이 누구인지 답할 수 없다).

## 4. 세계 역사 — `WorldHistory`

### 4-1. 사건 한 줄: `WorldEvent`

```
Id
Day            GameTimeManager.CurrentDay
Type           WorldEventType (끝에만 붙인다 — 정수 직렬화)
Actor          누가 했나   "player" / 세력 Id / 폰 Id
TargetFaction  누구의 일인가 (그 세력의 소굴·마을·사람)
Place          어디서     사이트 Id (없으면 좌표)
Involved       [(폰 Id, 역할)]   역할: Subject(당사자) / Victim / Witness / Beneficiary
Scope          얼마나 퍼지나 (고정 — 4-2)
Importance     정렬용 무게
Count          합쳐진 횟수 (4-4)
```

### 4-2. 범위는 고정 — 종류가 정한다

| Scope | 아는 폰 |
|---|---|
| `Involved` | `Involved`에 든 폰만 |
| `Site` | + 그 장소가 고향인 폰 (`HomeSiteId == Place`) |
| `Faction` | + `TargetFaction` 소속 전원 |
| `Region` | + `Place`에서 반경 R 안이 고향이거나 지금 거기 있는 폰 |
| `World` | 전원 |

종류별 기본 범위·호감 변화·반감기는 **표 하나**(`WorldEventTypeData`, 처음엔 코드 표도 된다)가 든다.
사건마다 따로 적지 않는다 — 같은 종류가 사건마다 다르게 퍼지면 화면으로 설명할 수 없다.

시간이 지나며 넓어지는 소문은 **1차에 넣지 않는다**(사용자 결정). 넣게 되면 `Scope`를 `Day`와 경과일로
계산하는 함수 하나만 바뀐다 — 저장 구조는 그대로다.

### 4-3. 첫 사건 종류 — 이미 있는 행동부터

| 종류 | 부르는 곳 | 범위 |
|---|---|---|
| `Ransomed` | `WorldRansom` (지금 `FactionRelations.Add` 자리) | Faction |
| `PrisonerReleased` | `PrisonCage` (같음) | Faction |
| `PawnKilled` | `UnitBrain` 사망 (같음) | Site |
| `Traded` | `Trading` | Involved |
| `Hired` | `Hireling` | Site |
| `Converted` | `Conversion` | Faction |
| `LairCleared` | `WorldBandManager` → `WorldLairs.Clear` | Region |

**구현(2026-11-18, 2단계)** — 위 일곱에 **`PawnExecuted`**(갇힌 채로 죽음)를 더했다: 값이 죽임(−12)과 달라(−25)
종류 표 하나로 답하려면 종류가 달라야 한다. `Hired`는 용병 계약(`Hireling.Sign`)과 돈 주고 데려오기(`Conversation.Hire`)
둘 다. `LairCleared`는 **지금 소굴이 병력을 다 내보냈을 때만** 난다(누구의 짓도 아니라 `Actor`를 비운다 — 플레이어가
쳐서 비우는 길은 5단계 `SiteRegistry`에서). 새 넷은 우호도를 안 움직인다.

**`FactionRelations.Add`를 부르는 세 곳은 사건을 적는 자리로 바꾼다** — 사건이 적히면 그 결과로 우호도가
움직인다. 이유 문자열이 사건으로 남고, 우호도 창에서 "왜"를 보여 줄 수 있다.

### 4-4. 색인과 합치기

- **색인 셋**: 폰 Id별(`Involved`) · 장소별 · 세력별. 대화를 열 때 한 번 조회한다.
- **합치기**: 범위가 `Involved`이고 오래된 같은 종류·같은 상대의 사건은 한 줄로 합친다
  (`Traded` 23번 → `Count = 23`, `Day` = 마지막). 큰 사건(`LairCleared` 등)은 합치지 않는다.

## 5. 앎과 개인 호감 — 계산한다

### 5-1. `Knows(record, ev)`

4-2의 표를 그대로 코드로 옮긴다. **결과를 캐시하지 않는다** — 처지(세력·고향)가 바뀌면 아는 것도 바뀌어야 한다.

### 5-2. 개인 호감 — 플레이어를 어떻게 보나

```
Opinion(record) = Σ (아는 사건)  종류의 호감 변화 × 역할 무게 × 흐려짐(경과일, 반감기)
```

| 어떻게 아나 | 무게 |
|---|---|
| Subject · Victim · Beneficiary (당사자) | 1.0 |
| Witness | 0.6 |
| 같은 장소 사람 | 0.4 |
| 같은 세력 | 0.25 |
| 지역 소문 | 0.1 |

- **세력 우호도와 분리한다**(사용자 결정). **적대 판정은 지금처럼 세력 숫자만** 본다.
  개인 호감은 **대화 · 가격 · 영입**에만 쓴다. "적대 세력인데 나를 좋아하는 사람"은 생길 수 있지만,
  그 사람도 싸울 때는 세력을 따른다.
- 같은 사건이 개인 호감과 세력 우호도 **둘 다의 원인**이 된다 — 원인이 하나라서 어긋나지 않는다.

### 5-3. 목격자 (1차 포함)

사건을 적는 쪽이 **그 자리 반경 안의 같은 세력 폰**을 `Witness`로 `Involved`에 넣는다. 시야 판정은
1차에 하지 않는다(`Vision`을 묻는 것은 나중에 같은 자리에서 조인다).

## 6. 사이트 상태 — `SiteRegistry` (영역 변화의 바탕)

지금 장소의 주인은 **계산된다** — `TownSite.ResolveFaction`이 경비병 → 아무 주민 → 바이옴 `TownFaction` 순으로
답하고, 소굴은 주인 세력이 없이 `WorldLairs`가 병력과 `_gone`만 든다. 주인이 바뀌는 일을 담으려면
**주인을 상태로 들 곳**이 필요하다.

```
SiteState
  SiteId
  OwnerFactionId   비우면 저작/계산된 주인 그대로 (저작 < 주입 — 상인 상품과 같은 규칙)
  Condition        Intact / Ruined / Empty / Occupied
```

- `TownSite.ResolveFaction`은 **`SiteRegistry`를 먼저 묻는다.** 비어 있으면 지금 순서 그대로.
- 소굴을 쓸면 `WorldLairs.Clear`와 함께 `Condition = Empty`, `LairCleared` 사건.

## 7. 세계 반응 — `WorldReactions` (나중)

사건이 **다음 사건을 부른다.** `WorldHistory.OnRecorded`를 듣고 조건에 맞으면 **며칠 뒤로 예약**한다.

```
LairCleared (A 세력 소굴)
   └ N일 뒤: 주변에서 A와 적대인 세력 B를 고른다
        SiteRegistry: Owner = B, Condition = Occupied
        WorldHistory: SiteClaimed (Actor = B, Place = 그 소굴, Scope = Region)
```

- **반응도 사건으로 적힌다** — 그래서 NPC가 *"그 소굴을 네가 쓸고 나서 오크들이 들어앉았다"*를 말할 수 있다.
- 무엇이 무엇을 부르나는 **데이터**로 든다(규칙 표). 반응마다 코드를 짜지 않는다.
- **알려진 큰 일**: B가 차지한 소굴에 **B의 폰이 서려면** 소굴 내용물이 세력별로 갈려야 한다
  (지금은 `LairEntry.Band` 하나다). 반응의 *기록*은 1차 구조로 되고, *눈에 보이는 교체*는 그때 따로 한다.

## 8. 퀘스트와의 연결 (나중)

퀘스트 시스템은 아직 없다. 생기면 **결과를 사건으로 적기만** 한다.

- `QuestCompleted` / `QuestFailed` — `Involved`에 의뢰인(Beneficiary)·대상, 범위는 퀘스트 데이터가 든다.
- 저작된 퀘스트 대사도 역사를 조건으로 읽는다(*"`LairCleared`가 있으면 이 줄"*).
- 다른 NPC가 그 이야기를 꺼내는 것은 5절의 앎이 그대로 해 준다 — 퀘스트용 기억을 따로 두지 않는다.

## 9. 떠난 폰의 재등장 (1차 포함)

떠돌이를 세울 때(`EventManager`) **`Departed` 기록 중 플레이어와 얽힌 사건이 있는 폰**을 먼저 확률로 뽑는다.
뽑히면 그 기록의 Spec·Body로 세운다(`Attach`가 알아서 입힌다).

→ *"예전에 풀어 준 포로가 떠돌이로 찾아온다"* · *"쫓아낸 용병이 다시 지나간다"*가 여기서 나온다.

---

## 10. 세이브 규약 — 지금부터 지킨다

- `PawnRecord` · `WorldEvent` · `SiteState`에는 **오브젝트 참조를 넣지 않는다.** 특성·출신·아이템·세력은
  **에셋 Id**로만 가리킨다(`docs/data.md`의 규약).
- 그러면 세이브는 **레지스트리 셋 + 카운터를 JSON으로 쓰는 것**으로 끝난다.
- **역사에는 문장을 저장하지 않는다 — 사실만 저장한다.** 사건은 종류·Id·숫자로만 적고, 화면에 보이는 문장은
  볼 때마다 그 언어의 번역표로 만든다. AI가 만든 대사도 저장하지 않는다(언어를 바꾼 플레이어에게 옛 언어가 남는다).

## 11. 단계 — 단계마다 화면에서 확인할 수 있게

| 단계 | 하는 일 | 확인 |
|---|---|---|
| 1 | `PawnSpec.Id` · `PawnRegistry` · Attach/Detach · `Placed`가 처지를 묻기 | 마을 사람을 죽이고 멀리 갔다 와도 **다시 서지 않는다** |
| 2 | `WorldHistory` · 4-3의 사건 일곱 · `FactionRelations.Add` 세 곳 교체 · 디버그 창 | 사건 목록 창에 줄이 쌓인다. 우호도 변화에 이유가 붙는다 |
| 3 | `Knows` · 개인 호감 · 목격자 · 살펴보기 창에 호감 표시 · `Conversation.Greeting`을 호감 구간별 고정 대사로 | 거래를 많이 한 상인과 처음 보는 상인의 첫마디가 다르다 |
| 4 | 떠난 폰 재등장 | 풀어 준 포로가 떠돌이로 다시 온다 |
| 5 | `SiteRegistry` · `LairCleared` · `WorldReactions` 뼈대 | 소굴을 쓸고 며칠 뒤 `SiteClaimed` 사건이 적힌다 |

**진행** — 1~5단계 구현(2026-11-18 · Play 확인 대기). 4단계는 떠돌이 이벤트에서 35%로 뽑고 같은 종족 몸에만 세운다. 5단계의 반응 규칙은 `WorldReactions.Rules` 한 표(지금 하나 — 소굴이 빈 3일 뒤 600m 안의 적대 이웃이 차지). 3단계의 호감 값(종류마다 · 반감기)은 `WorldHistory.RuleOf` 한 표에 있다. 지금 세계에 저작된 자리의 폰이 없어 1단계 확인은
디버그 창 `폰 기록`의 시험 마을 사람(`WorldContentStreamer.DebugPlace`)으로 한다.

그다음이 **세이브**(10절), 그다음이 **AI 대사**(13절).

## 12. 1차에 하지 않는 것

- 시간이 지나며 퍼지는 소문
- 세력끼리의 관계 변화 (`FactionRelations`는 여전히 플레이어와의 관계만 움직인다)
- 차지한 소굴에 다른 세력 폰이 실제로 서는 것 (7절)
- 화면 밖 폰의 생활 시뮬레이션 (기록은 *멈춰 있다* — 다시 만날 때 그때의 몸으로 선다)
- 되살아난 시체(`Necromancy`)와 원래 사람의 연결

## 13. AI 대사 — 로컬 소형 모델 (세이브 다음)

2026-11-16 결정. **AI는 "있으면 더 좋은 것"이다** — 꺼져 있거나 실패하면 3단계의 고정 대사가 그대로 나온다.
게임은 AI 없이 완전해야 한다.

### 13-1. AI가 하는 일은 하나

**"주어진 사실 두세 개를 이 인물 말투로 한두 문장으로 말하기."**

- 선택지와 그 결과는 코드가 정한다(`Conversation`) — AI는 선택지를 만들지 않고 게임 상태를 바꾸지 않는다.
- 사실은 `WorldHistory`가 준다(5절의 앎 — 아는 사건 중 중요도·최근 순 상위 몇 개). **입력에 없는 것을 말하면 버린다**(13-6).
- 긴 대화·자유 입력은 하지 않는다 — 작은 모델이 무너지는 자리이고, 콜로니 심의 흐름에도 안 맞는다.

### 13-2. 모델 — Qwen3.5 하나

| 후보 | 4비트 크기 | 비고 |
|---|---|---|
| **Qwen3.5 0.8B** | 약 0.5GB | 작은 쪽. 압축을 덜 해도(8비트) 1GB 안쪽 |
| **Qwen3.5 2B** | 약 1.5GB | 큰 쪽 |

- **Apache 2.0** — 파인튜닝한 모델을 게임에 넣어 팔 수 있다. 조건은 라이선스·고지 파일 동봉과 수정 표시뿐.
- **모델은 하나만 넣는다** — 플레이어가 고르지 않는다. 다국어 모델이라 언어가 늘어도 모델은 그대로다.
- **둘 중 무엇인지는 시험 세트가 정한다**(13-7). 같은 용량 근처에서 Labyrinth 대사를 더 잘 쓰는 쪽.
- **고르기 전에 확인할 것**: 쓰는 llama.cpp 버전이 Qwen3.5 구조를 지원하는가 · 텍스트 전용으로 변환하면 이미지 처리 부분이
  빠지는가(대사만 쓴다).
- **뺀 것과 이유**: Kanana(온디바이스 탑재에 카카오 별도 계약 필요 · "Powered by Kanana" 표시 · 파생 모델 이름 규칙) ·
  Gemma 4(가장 작은 E2B도 너무 크다) · Mistral NeMo Minitron(inZOI의 0.5B는 공개되지 않았고 공개된 8B는 너무 크다).

### 13-3. 파인튜닝 — 작은 모델을 Labyrinth 대사만 잘하게

1. **입력 형식을 먼저 고정한다** — 인물(이름·역할·특성) · 말투 · 아는 사건 · 지금 상황 · 규칙. 학습 데이터가 전부 이 형식이라
   형식이 바뀌면 데이터를 다시 만든다. 그래서 **학습은 3단계(앎·호감)가 끝난 뒤다.**
2. **학습 전 기준점** — 후보 둘을 학습 없이 시험 세트에 돌린다.
3. **세력별 말투는 모델에 굽지 않는다** — 세력이 늘어도 모델은 안 바뀐다. 세력별 말투·금기어·고정 대사는
   **데이터 카드(`VoiceCard`)** 로 두고 프롬프트에 넣는다. 파인튜닝은 "카드의 말투와 사실을 지켜 한두 문장으로 말하기"라는
   능력만 가르친다 — 세력을 굽으면 세력을 추가할 때마다 데이터를 만들고 다시 학습해야 한다.
   대신 소형 모델이 카드를 안 따를 수 있으므로 **학습 데이터에 카드가 다양한 예를 충분히 넣는다**(세력 수보다 이게 더 큰 변수).
4. **데이터는 조합으로 만든다** — 종족·세력·역할·특성·사건 종류를 코드로 섞어 상황 수천 개, 대사는 큰 모델이 쓴다.
   일부를 직접 읽어 Labyrinth답지 않은 것을 거른다. 출시 언어(최소 한국어·영어) 데이터를 다 만든다.
   **데이터를 만든 서비스의 약관이 이 사용을 허용하는지 확인한다.**
5. **LoRA로 학습한다** — Colab이나 시간제 GPU로 충분하다(Unsloth · TRL).
6. **합치기 → GGUF → 압축** → 같은 시험 세트로 다시 돌린다.

### 13-4. 게임에 붙이는 구조

```
StreamingAssets/AI/
  bin/llama-server.exe        Vulkan 빌드 (NVIDIA·AMD·인텔 GPU 모두, CUDA 라이브러리 불필요)
  labyrinth-npc.gguf          파인튜닝 결과물
  LICENSE, NOTICE             Apache 2.0 고지

LlmProcess    서버를 띄우고 끈다
LlmService    대기열 · HTTP · 시간 초과 — **엔진을 아는 유일한 곳**
PromptBuilder 폰 기록 + 아는 사건 + 상황 → 프롬프트 (ModelProfile · 번역표)
LineFilter    결과 검사 → 통과 못 하면 고정 대사
Conversation  첫마디를 받아 띄운다 (실패하면 고정 대사)
```

- **별도 프로세스로 돌린다.** AI가 죽어도 게임은 산다. AI를 끄면 프로세스를 끄는 것으로 메모리가 확실히 돌아온다.
  콜로니 심은 한 판이 길어서 *AI 크래시 = 게임 크래시*가 가장 비싸다.
- **`LlmProcess`**: 빈 포트를 골라 띄우고 `/health`로 준비를 확인한다. **CPU 스레드는 코어의 절반쯤으로 묶는다**(안 묶으면
  프레임이 떨어진다). **게임이 강제 종료돼도 서버가 같이 죽게 한다**(Windows Job Object) — 안 하면 플레이어 PC에 프로세스가 남는다.
- **`LlmService`**: 직접 건 대화 > NPC끼리 대화 순. 시간 안에 안 오면 버린다. **엔진을 바꿀 때 고칠 곳은 여기와 학습의 마지막
  변환 단계뿐이다** — 나머지는 엔진을 모른다.
- **미리 만든다**: 폰을 선택하거나 우클릭 메뉴를 열 때 요청한다. 결과는 폰 × 상황으로 캐시한다. 그래도 늦으면 고정 대사로 창을
  먼저 열고 받는 대로 바꾼다.

### 13-5. 프롬프트 — 내용과 모델 설정을 가른다

- **내용(모델과 무관)**: `PromptBuilder`가 만든다. 사건 설명·말투 설명 문장은 **언어별 번역표**에서 온다.
  게임 언어가 영어면 영어로 받고 영어로 말한다 — **AI 대사를 번역하지 않는다.**
- **모델 설정(`ModelProfile`, 데이터)**: 생성 설정(온도 등) · 생각 모드 끄기 · 예시 대사(few-shot, 언어별) · 시스템 지시문 문구.
  출시 때는 하나지만 데이터로 두면 후보 비교와 모델 교체가 프로필 교체로 끝난다.

- **세력 추가 비용(데이터 작업, 코드 아님)**: 세력마다 `VoiceCard` 한 장(어휘·태도·금기어 3~5줄) · 고정 대사 몇 줄 ·
  `LineFilter` 말투 규칙 · 시험 상황표 행 · 의견 계산의 역할 가중치 행. 실행 비용(모델·메모리·속도)은 세력 수와 무관하다 —
  프롬프트에는 말하는 사람의 세력 카드만 들어간다. 말 못 하는 야수는 AI 대사 대상이 아니다.

### 13-6. `LineFilter` — 플레이어가 이상한 답을 보지 않게

길이 초과 · 다른 언어 섞임 · 생각 태그 잔여 · **입력에 없는 이름·장소** · 말투 어미(하오체 등) 이탈 → 하나라도 걸리면 고정 대사.

### 13-7. 시험 도구

에디터 창 하나에서 시험 세트 전체(상인·포로·떠돌이 × 호감 구간 × 사건 2~3개, 20~30개부터)를 실행 중인 서버에 돌리고 결과를
표로 남긴다. **모델 고르기 · 파인튜닝 전후 비교 · 모델 교체에 같은 도구를 쓴다.**

### 13-8. 설정과 성능 — inZOI(Smart Zoi, 0.5B, VRAM 약 1GB)에서 가져온 것

- **기본은 꺼짐** — 옵션의 실험 기능으로 켠다.
- **배속 제한** — 빠른 배속에서는 NPC끼리 대화 같은 추론을 멈춘다(Labyrinth는 10배속까지 있다). 직접 건 대화만 남긴다.
- **화면 범위 제한** — 추론은 `SimLocality`가 도는 곳에서만.
- **VRAM 확보** — 켜면 그래픽 설정(`ShadowBudget` 등)을 한 단계 낮춘다.
- **하드웨어 판단은 세 갈래** — VRAM에 여유가 있으면 GPU · 아니면 CPU · RAM도 모자라면 끈다.
- **GPU 회사에 묶이지 않는다** — inZOI는 NVIDIA ACE라 RTX에서만 돈다. Labyrinth는 llama.cpp Vulkan으로 간다.

### 13-9. 순서

`설계 1~5단계` → `세이브` → 입력 형식 확정 → 시험 도구 + 학습 전 기준점 → 데이터 생성 → LoRA → 게임 연동(13-4) → 설정(13-8).
기준점 측정은 입력 형식 초안만 있으면 **더 일찍** 해도 된다.
