## 2026-07-31 (4) — 시계·배속 HUD + 건설 목록 확충

### 1. 시간이 흐르는지 알 수가 없었다
`GameTimeManager`는 돌고 있었지만 **화면에 아무 표시가 없었다.** 게다가 하루가 `dayDuration` 3600초(실제 60분)라 "하루 뒤 채집기지에 자원이 쌓인다"를 확인할 방법 자체가 없었다.

- **`TimeHUD`(신규)** — 상단 가운데에 `3일차 14:20 낮`. `OnTimeChanged` 구독.
- **배속** — `GameTimeManager.SetSpeed`가 `Time.timeScale`을 직접 만진다. 시간의 주인이 거기이고, 폰 행동·건설·채굴이 전부 deltaTime을 따르므로 **게임 전체에 똑같이** 걸린다(시계만 빨라지지 않는다). 정지·1배·3배·10배. 스페이스 = 일시정지 토글(풀면 직전 배속 복귀).
- **시각 표기는 6시를 하루의 시작으로** 잡았다. `IsDay`가 `NormalizedTime < 0.5`라, 0을 0시로 두면 "낮인데 새벽 3시"가 된다 → 낮 06:00~18:00 / 밤 18:00~06:00.
- `GameTimeManager`에 싱글톤 가드와 `OnDestroy`의 `timeScale = 1` 복구를 넣었다 — 멈춘 채로 플레이를 끝내면 에디터가 얼어붙은 것처럼 보인다.

### 2. 작업대·연구대·나무를 건설할 수 없었다
건설 목록에 8종뿐이었고 **작업대와 연구대는 프리팹조차 없었다**(씬에만 존재). 그래서 씬 인스턴스를 프리팹으로 저장하는 단계를 넣었다.

- `Add Missing Buildings` — 무기 제작대 / 용광로 / 조리대 / 연구대 / 나무 심기.
- **작업대는 종류마다 프리팹이 하나씩 필요하다.** `BuildingData`에 스킬 칸이 없어서 "무엇을 만드는 작업대인가"는 프리팹(`CraftingTable.tableType`)이 들고 있어야 한다. 씬의 세 작업대(WeaponCrafting·Smelting·Cooking)를 각각 저장했다.
- 프리팹은 **켜진 상태로** 저장한다 — 원본이 씬에서 꺼져 있어 그대로 저장하면 배치해도 안 보인다.
- 이미 있는 프리팹/데이터는 **덮어쓰지 않는다**(인스펙터에서 손봤을 수 있다).
- 전부 `OccupiesTile = true` — 유닛이 통과하지 못하는 실체 건물.

### 3. 마무리 — 커밋 후 생성기 정리
07-29부터 쌓인 279개 변경을 두 커밋으로 나눴다(기능/씬/문서 · 데이터 에셋). **커밋 뒤에** 역할을 마친 일회성 생성기 6개를 삭제했다 — 커밋 전에 지우면 미추적 파일이라 git에서 못 꺼낸다.

- 지움: `DataScaffoldCreator` · `DataCleanup` · `BuildContentCreator` · `TimeHudCreator` · `ExpeditionPanelCreator` · `UiConventionSweep` (전부 씬에서 산출물 확인 후)
- 남김: `World Map Editor`(상시 저작) · `Setup World Map Scene`(복구) · `Create Biome Content Assets`(바이옴 추가 시) · `Toggle Movement Diagnostics`(검증 중)

### 미결
- **Terrain 활성화 여부는 사용자 검토 중** — 던전 구성(바닥 시스템)이면 그대로 두고 `HierarchicalPathfinder`의 경고 문구를 바꾸는 게 낫다.
- **채집기지 전체 루프가 아직 미검증** — 데이터가 다 찼고 시계·배속도 생겼으니 이제 확인 가능하다.
  편성 → 도착 → 탐험 → 자동 건설 → (10배로) 하루 → 비축분 싣기 → 거점 입고.
- 07-30 (3)의 **지형 검증**(맵이 한 장으로 이어져 보이는지, 여러 칸 산맥이 나오는지)도 아직.

## 2026-07-31 (3) — 빠진 콘텐츠 데이터 일괄 생성 + 잔재 정리

"귀찮아서 안 만든 데이터"를 한 번에 채웠다. `DungeonColony → Create Missing Data`(`DataScaffoldCreator`) — **없는 것만 만들고 기존 에셋은 손대지 않는다.** 결과 **신규 86 / 기존 재사용 5**.

만든 것과 **관계도·바이옴별 성격 표는 `docs/data.md`** 하단에 정리했다(여기 옮기지 않는다 — 데이터 문서가 정본).

큰 줄기: 자원 아이템(ResourceType 22종) · 작물/음식 7 · 씨앗 3 · 무기 11 · 방어구 8 · 자원 노드 10 · 레시피 10 · 연구 6 · 바이옴 7종의 매장/노드 풀.

### 발견 — `ResourceType` enum 드리프트
`Ore_item`이 **CutStone**, `Crystal_item`이 **CopperOre**였다. enum에 값이 끼워 넣어지면서 **저장된 정수의 의미가 밀린** 것. 이름만 옛 뜻으로 남아 있었다.
- 확인해보니 **타입은 모든 참조에서 일관되게 맞물려 있었다**(레시피 재료·노드 드롭·바이옴 매장). 그래서 **이름만 고쳤다** — 참조는 하나도 안 건드렸다.
- 규칙으로 남김: **`ResourceType`에 값을 중간에 끼워 넣지 말고 끝에 추가할 것.**

### 밟은 함정 — 비활성 오브젝트를 못 찾았다
잔재 정리(`DataCleanup`)에서 `FindFirstObjectByType<ResearchTable>()`이 **비활성을 제외**하는 걸 놓쳤다. 이 씬의 연구대는 `Settlement_0` 아래에 꺼진 채로 있어 "씬에 없습니다"로 건너뛰었고, 그 상태로 연구 에셋을 지워 **목록에 빈 항목을 남겼다.**
→ `FindObjectsByType(FindObjectsInactive.Include, …)` + 여러 개 전부 처리로 고치고 재실행해 복구. `docs/editor_creators.md`에 규약으로 명문화.

### 지운 것 (전부 GUID 역참조로 "쓰이지 않음" 확인 후)
`5_Data/Resource/Ore.asset` · `Crystal.asset`(새 `Node_*` 세트로 대체) / `Resources/Data/Research/New Research Data.asset` / `Resources/Data/Biome/`(폴더가 단수라 로드되지 않던 것) — 그리고 사용자가 `5_Data/Item/`을 직접 삭제.

### 설계 교정 — 테이블은 **레지스트리에서 끌어온다**
사용자 질문("씬에 배치된 테이블에만 데이터를 넣는 게 맞아? 나중에 건설하는 건 비는 거 아니야?")으로 드러난 실제 결함. 두 테이블이 서로 다른 방식을 쓰고 있었다.

| | 목록 출처 | 판정 |
|---|---|---|
| `CraftingTable` | `DataManager.GetRecipesBySkill(tableType)` | 옳음 — 인스턴스엔 "어느 스킬의 작업대인가"만 |
| `ResearchTable` | `[SerializeField] List<ResearchData>` | **틀림** — 인스턴스마다 손으로 채워야 함 |

지금은 두 테이블 다 `5_Data/Building/`에 없어 **건설이 안 되니 드러나지 않았을 뿐**이고, 연구대를 건설 가능하게 만드는 순간 빈 목록이 나온다.

→ `ResearchTable.AllResearch`가 목록이 비면 **`DataManager.AllResearch` 전체**를 쓰도록 고쳤다(없던 접근자도 추가). 채우면 그게 이기는 **큐레이션용 오버라이드**로 남겼다 — "데이터가 없으면 기본 동작"이라는 관례(`BiomeContentData`·`WorldTileVisualData`)와 같은 규칙. 씬의 목록은 비워 레지스트리를 따라가게 했다.

**새 테이블을 만들 때도 같은 규칙**: 인스턴스에는 "무엇을 다루는 테이블인가"만 두고 목록은 레지스트리에서. `docs/data.md` 앞부분에 `5_Data` vs `Resources/Data` 구분과 함께 절로 정리.

### 남은 것
- **아이콘·월드 모델이 전부 비어 있다**(만들 수 없는 자산). 인벤토리에서 빈 칸으로 보인다.
- 값은 전부 임시 초안 — 밸런스는 인스펙터에서.
- `ResearchTable`·`CraftingTable`은 아직 **건설 불가**(`5_Data/Building/`에 없음). 건설 가능하게 만들 때 프리팹부터 필요하다.

## 2026-07-31 (2) — 방향 수정: 자원은 "특별한 칸"이 아니라 **어느 칸에나 묻혀 있다**

(6)에서 만든 채집은 `ResourceSite`로 저작한 칸에서만 되는 **전용 행동**이었다. 사용자가 원한 건 **아무 칸에나 들어가 자리를 잡고 캐는 것**이었다 — 전제가 달랐다. 자원 획득의 축을 "특별한 칸의 버튼"에서 "칸마다의 매장량 + 그 위에 세우는 시설"로 옮긴다.

**용어**: `자원 기지 건설` → **전초기지**. 이 게임이 이미 쓰는 **거점**(사람이 사는 정착지)과 구분된다 — 전초기지는 자원을 캐려고 밖에 박아두는 곳.

### 1. 매장 자원 데이터 — 바이옴이 종류를, 좌표가 수량을
- `BiomeContentData.Deposits`: 자원 + 출현 확률 + 매장량 범위.
- `WorldDeposits.At(node, tile, seed)`: 실제 수량은 **칸 좌표 + 시드 해시**로 결정적으로 굴린다. 256칸을 손으로 채우지 않아도 칸마다 다르고, 다시 실행해도 같은 값이 나온다(세이브 없이 일관).
- **"지도를 절차 생성한다"와 다르다** — 배치(바이옴·내용물)는 여전히 저작물이고, 여기서 뽑는 건 그 저작된 칸의 세부 수치뿐이다.
- 항목마다 **다른 난수열**을 쓴다. 같은 열이면 모든 자원이 함께 나오거나 함께 빠져 매장 조합이 단조로워진다.
- `ResourceSite`로 저작한 칸은 매장량 ×2.5 — "자원 지대"라고 찍어둔 것이 실제로 의미를 갖게.

### 2. 탐험 = 조사 (안개가 아니라 **세부 은닉**)
`WorldMap.IsSurveyed` / `MarkSurveyed`. 지형·바이옴·내용물은 06-20 결정대로 처음부터 다 보이고, **가려지는 건 매장량뿐**이다. 조사 전엔 `매장 자원 — 미조사`. 이래야 "어디에 전초기지를 세울까"를 정하려고 발품을 팔 이유가 생긴다.

### 3. 메뉴가 **모든 칸에서** 열린다
전엔 `Content != Empty`인 칸에서만 열렸다. 아무 데나 자리를 잡으려면 빈 야생에서도 할 일이 있어야 한다 → 그 조건을 걷어냈다. 빈 칸의 제목은 "빈 지역" 대신 **바이옴 이름**.
- 정보 영역에 매장 목록을 여러 줄로 얹었다 — `WorldMenuPanel`은 손대지 않았다(`Info` TMP가 늘어난다).
- 선택지: `탐험한다`(조사) / `여기에 전초기지를 세운다`. 막힐 땐 이유가 각각 다르다 — `이미 조사함` / `동행 없음` / `먼저 탐험해야` / `캘 것이 없다` / `준비 중`.
- **자원 지대 전용 채집은 제거**했다. 자원 얻는 길이 두 갈래로 갈리면 규칙이 흐려진다. `ExpeditionParty.Cargo`와 `UnloadCargo`는 남겨 뒀다 — 전초기지에서 실어오는 흐름이 붙으면 다시 쓰인다.

### 4. **채집기지** — 자동 건설은 필드맵 없이 굴러간다
이름은 `전초기지` → **`채집기지`**(사용자 안). 이미 쓰는 **거점**(사람이 사는 정착지)과 구분된다. `작업장`은 **작업대**(CraftingTable)와 헷갈려 뺐다. 매장에 목재가 많아지면 `채집기지`로 한 단어만 바꾸면 된다.

`여기에 채집기지를 세운다`를 누르면 **건설 방식 서브메뉴**로 갈아탄다(M&B의 메뉴 안 메뉴). `WorldMenuPanel`은 목록만 그리므로 패널 수정 없이 내용만 바꿔 끼웠다.

- **자동 건설** — 동작한다. `OutpostManager`가 그 칸의 매장을 실은 추상 시설을 세우고(`WorldNodeContent.Outpost` 신설), **매일(`OnDayChanged`) 알아서 캐서 기지에 쌓는다.** 들어갈 필요가 없다.
  - **본거지로 순간이동하지 않는다.** 쌓인 것은 기지에 남고, 원정대가 들러 `비축분을 싣는다`로 등짐에 실어 와야 창고에 들어간다 — 설계의 "거점 간 물류: 1차는 파티 등짐만"과 같은 규칙이고, 덕분에 등짐이 다시 살아났다.
  - 하루치는 남은 매장에서 **골고루** 덜어낸다. 한 자원만 먼저 파내면 "이 기지가 무엇을 주는가"가 날마다 달라져 읽기 어렵다.
  - 건설 비용은 `OutpostManager.buildCost`(비우면 무료). 서브메뉴 정보란에 `비용 — 철 12/20`처럼 **가진 양/필요 양**을 그대로 보여준다.
  - 매장이 다하면 고갈 로그 + 메뉴에 `매장 고갈`.
- **직접 건설** — `준비 중 · 필드맵 생성 필요`. 그 칸에 실제 필드맵을 만들어 들어가 짓는 길이고, 아래가 전제다.

### 남은 것 — 직접 건설(진짜 필드맵)
- **가능성은 확인됐다**: `MapManager.SetAsPlayerZone` / `DungeonCore.SetAsActive`가 이미 다중 인스턴스를 전제한다.
- **없는 것**: 정착지 템플릿 프리팹. 씬의 `core`는 프리팹 인스턴스가 아니고 코어 프리팹 자체가 없다(`3_Prefab`에 `sub.prefab`만).
- 그 밖: `JobManager._jobs`가 전역 리스트라 거점이 둘 이상이면 남의 일감이 섞인다(07-29 "알려진 잔여") — 이때 정리해야 한다.

### 검증 필요
1. `BiomeContentData.Deposits`를 채운 뒤(지금 7개 전부 비어 있음) → 그 바이옴 칸에 도착 → 메뉴에 `매장 자원 — 미조사`가 뜨는지.
2. [탐험한다] → 매장 목록이 그 자리에서 드러나는지. 다시 누르면 `이미 조사함`으로 막히는지.
3. **빈 야생 칸에서도 메뉴가 열리는지**(제목이 바이옴 이름인지).
4. 같은 칸을 껐다 켜도 매장량이 **같은지**(결정적). `WorldMap.depositSeed`를 바꾸면 수량만 달라지고 바이옴 배치는 그대로인지.
5. 자원 지대(3,8)의 매장량이 같은 평원 칸보다 확실히 많은지(×2.5).
6. 매장이 없는 칸에서 [여기에 채집기지를 세운다]가 `캘 것이 없다`로 막히는지, 조사 전엔 `먼저 탐험해야`인지.
7. `Setup World Map Scene` 실행 → `OutpostManager`가 붙는지. 조사한 칸에서 [여기에 채집기지를 세운다] → **건설 방식 메뉴**로 갈아타는지(비용·매장이 보이는지), [돌아가기]로 되돌아오는지.
8. [자동 건설] → 지도에 채집기지 마커가 서고 칸 내용물이 바뀌는지. **하루 지나면 비축이 쌓이는지**.
9. 그 칸에 다시 들러 [비축분을 싣는다] → 등짐이 차는지. 등짐 한도를 넘으면 **기지에 남는지**.
10. 거점 복귀 → 등짐이 창고로 들어가는지(기존 `UnloadCargo` 경로가 이번에 처음 실제로 쓰인다).
11. 매장을 다 캐면 `매장 고갈`로 바뀌고 더 안 쌓이는지.
12. `buildCost`를 채우면 부족할 때 [자동 건설]이 `철 부족`처럼 막히고, 지으면 창고에서 실제로 빠지는지.

## 2026-07-31 — 집결이 "대기" 상태로 멈추던 버그: 높이 차 + 못 오는 폰

증상: [출발]을 누르면 폰이 조금 가다 "집결 대기"로 서 버리고 원정이 시작되지 않는다. 원인이 둘 겹쳐 있었다.

### 1. 도착 판정이 3D 거리였다 (핵이 떠 있다)
집결 지점은 `DungeonCore.GetSpawnPosition()` = **핵 위치 + 수평 2유닛**인데, 핵은 `_hoverOffset`만큼 **떠 있다**(2026-07-27 (3)에서 넣은 저작 부양 높이). 그 Y가 그대로 목적지에 실려서:
- 폰이 발밑까지 와도 높이 차 때문에 `arriveRadius`(1.8) 안에 안 들어오거나,
- 반대로 목적지가 공중이라 길찾기가 닿을 수 없는 자리로 보고 중간에 포기했다.

→ **도착 판정을 수평 거리로** 바꾸고, 집결 지점을 **표면에 스냅**한다.

- 스냅은 `SampleGroundHeight`가 아니라 **`SurfaceHeight`**를 쓴다. 이 씬은 Terrain을 끄고 바닥 시스템(`[DungeonStarterFloor]`)으로 도는 던전 구성이라 `SampleGroundHeight`가 0(평지 가정)을 돌려준다 — 바닥 위에 선 폰과 집결 지점의 높이가 어긋난다. `SurfaceHeight`가 "바닥 윗면 ∥ 지형 높이"의 단일 출처다.

### 2. 한 명이 못 오면 전체가 영영 멈췄다
길찾기가 포기하면 `PawnMover`는 목적지를 잃고 그냥 선다. 그 폰은 영영 도착하지 않는데 출발 조건은 "전원 도착"이라 **편성이 걸린 채 방치**됐다.

→ `NudgeStragglers`: 목적지를 잃은 채 아직 도착 안 한 폰을 `nudgeInterval`(2초)마다 **계속 다시 명령**하고(길이 뚫리면 알아서 온다), `stuckAfterNudges`(3회) 뒤에도 못 오면 **"갈 수 없음"으로 알린다.**

- **두고 출발하지 않는다.** 처음엔 그렇게 만들었다가 사용자 지적으로 되돌렸다 — 몰래 빼면 "왜 얘가 안 갔지"가 되고, 플레이어가 고른 명단을 시스템이 임의로 줄이는 셈이다. 판단(취소할지, 길을 뚫을지)은 플레이어 몫이다.
- 알림은 **패널 상태줄**에 `'라핀' 외 2명이(가) 집결 지점에 갈 수 없습니다 — 취소하거나 길을 확보하세요`로 뜨고 색이 경고색으로 바뀐다. 패널을 닫아둔 채였다면 **편성당 한 번 자동으로 띄운다**(매번 띄우면 사용자가 닫는 것과 싸운다).
- 막혔다가 길이 뚫려 다시 걷기 시작하면 표시를 거둔다.
- 집결 중에 패널을 열면 **가고 있는 폰이 체크된 채로** 보인다(`ExpeditionFormation.Members` + `SetIsOnWithoutNotify`) — 안 그러면 빈 목록처럼 보인다.

### 3. 파티 토큰이 하늘로 날아갔다 — 토큰이 자기 자신을 밟았다
(8)에서 팀 클릭 선택을 넣으며 토큰의 콜라이더를 **살려 뒀는데**(전엔 만들자마자 지웠다), `WorldMapGrid`의 표면 레이캐스트는 위에서 아래로 쏜다. 그래서 **토큰이 자기 콜라이더를 먼저 맞고** 그 위로 올라가고, 다음 프레임엔 더 위에서 맞고… 매 프레임 `tokenHover + size`씩 상승했다.

→ 토큰 콜라이더를 **트리거로** 둔다. 표면 레이캐스트는 `QueryTriggerInteraction.Ignore`라 트리거를 못 보므로 되먹임이 끊기고, 클릭 선택은 그대로 된다(선택 쪽 `RaycastAll`은 `Collide`를 명시해 트리거까지 받는다 — 프로젝트 전역 설정에 기대지 않게).
- 덤으로 `TryPickTerrain`이 **트리거를 걸러낸다**. 지형은 솔리드 콜라이더이므로, 앞으로 트리거 장식을 얹어도 이동 명령이 막히지 않는다.
- 레이어를 새로 파지 않았다 — 프로젝트 설정을 건드리면 씬마다 다시 맞춰야 한다.

### 확인한 씬 사실 — Terrain이 꺼져 있다
`[HierarchicalPathfinder] Terrain 없음` 경고의 정체: **씬의 `Terrain` 오브젝트가 `m_IsActive: 0`**(Settlement_0 아래). `Terrain.activeTerrain`은 활성 지형만 돌려주므로 null이 된다.
- 영향: `HierarchicalPathfinder._l2`가 빈 100×100 격자(원점)로 초기화 → **광역(L2) 경로가 사실상 없다.** `MapManager.SampleGroundHeight`도 terrain 경로를 잃는다.
- 다만 `[DungeonStarterFloor]` 2개가 활성이라 바닥 시스템으로 굴러가는 중이므로 **의도된 던전 구성일 수 있다** — 임의로 켜지 않고 사용자 판단으로 남긴다. 켜야 한다면 인스펙터에서 활성화하면 경고가 사라진다.

## 2026-07-30 (8) — 원정대 **여러 팀**: 토큰은 나가 있을 때만, 선택은 필드맵과 같게

(7)의 편성이 동작 확인된 뒤 나온 세 가지 요구를 처리했다. 핵심은 **원정대가 하나라는 전제를 버린 것**이다.

### 1. 로스터 — 원정 나간 폰은 빠지고, 돌아오면 다시 붙는다
나간 폰은 GameObject가 꺼져 있어 클릭해도 선택·명령이 안 되고 상태 표시도 떠날 때 그대로 멈춰 있었다 — 죽은 줄이 된다. `RefreshAll`에서 `activeInHierarchy`가 아닌 행을 걷어낸다.
- **복귀는 재탐색으로 줍는다.** `OnUnitSpawned`는 최초 스폰 때만 오고, 비활성 오브젝트는 기본 검색에서 빠지므로 "돌아왔다"를 알려주는 이벤트가 없다. 로스터가 어차피 0.3초마다 갱신하므로 그 김에 훑는다.

### 2. 토큰은 나가 있는 팀이 있을 때만 선다
전엔 `Start`에서 토큰을 하나 만들어 **아무도 안 나갔는데 지도에 서 있었다**. 이제 `AddMembers`가 팀을 만들 때 토큰이 생기고, 거점에 들어가면 팀과 함께 사라진다(`RemoveParty`).

### 3. 여러 팀 + **필드맵과 같은 선택 조작**
`WorldMapView`가 들고 있던 단일 `_party`를 `List<PartyToken>`으로 바꿨다(파티 + 토큰 + 이동 상태 묶음).
- **좌클릭 = 단일 선택 / 드래그 = 사각 다중 선택 / 빈 곳 = 해제** — `SelectionManager`와 같은 규칙(추가 선택 수정자 없음도 동일). 선택한 팀은 색이 밝아진다.
- **우클릭 = 선택한 팀만 이동.** 여러 팀을 한 점으로 보내면 겹치므로 격자로 벌려 세운다.
- 드래그 사각형은 `WorldMapView`가 직접 `OnGUI`로 그린다 — 필드의 `SelectionBox`는 필드 전용이라 월드 모드에서 꺼져 있다.
- 도착 메뉴·채집·거점 진입이 전부 **그 팀 기준**으로 동작한다(`_menuParty`). 메뉴 정보줄에 인원과 등짐을 같이 띄운다.
- Enter 단축키는 **정확히 한 팀만 선택했을 때만** 연다 — 여럿이면 누구 메뉴인지 모호하다.
- 채집 하루 제한은 **팀별이 아니라 칸별**로 뒀다. 팀별이면 여러 팀이 번갈아 긁어 제한이 무의미해진다.

### 밟은 함정 — 토큰 콜라이더
팀을 클릭하려면 토큰에 콜라이더가 있어야 하는데(전엔 만들자마자 지웠다), 그러면 **이동 명령 레이캐스트가 토큰에 막힌다**. 레이어를 새로 파지 않고 `Physics.RaycastAll` + 거리순 정렬로 풀었다 — 팀 선택은 "토큰인 첫 충돌", 이동은 "토큰이 아닌 첫 충돌". 레이어 이름에 의존하지 않아 프로젝트 설정을 건드리지 않는다.

### 검증 필요
1. 아무도 안 나간 상태에서 M → **지도에 토큰이 없는지**.
2. 편성해서 내보내면 토큰이 생기고, 로스터에서 그 폰들이 **빠지는지**.
3. 두 팀을 따로 내보내 **토큰 두 개**가 되는지. 좌클릭으로 하나씩 골라지는지, 드래그로 둘 다 잡히는지, 빈 곳 클릭에 해제되는지.
4. 선택한 팀만 우클릭으로 움직이는지. 둘 다 선택해 보내면 **겹치지 않고 벌려 서는지**.
5. 각 팀이 자기 등짐으로 채집하는지(메뉴 정보줄의 인원·등짐이 팀마다 다른지).
6. 한 팀이 거점에 들어가면 **그 토큰만 사라지고** 다른 팀은 남는지. 로스터에 돌아온 폰이 다시 뜨는지.
7. 팀을 여럿 선택한 채 Enter를 눌러도 메뉴가 안 열리는지(하나만 선택했을 때만).

## 2026-07-30 (7) — 원정대 편성 UI + **집결**: 폰이 갑자기 사라지지 않는다

편성이 G키 한 번에 선택 유닛이 **그 자리에서 증발**하는 방식이었다. 사용자 지적대로 부자연스러워서, 고른 폰이 **던전 핵 앞으로 걸어와 모인 뒤 함께 떠나는** 단계를 넣었다(림월드의 대상 편성과 같은 구조).

### 1. `ExpeditionFormation`(신규) — 집결
- [출발] → 고른 폰들에게 **핵 앞 집결 지점**으로 이동 명령. 돌아올 때 스폰되는 자리와 **같은 지점**이라 나가고 들어오는 문이 하나로 읽힌다.
- 명령 방식은 **플레이어 이동 명령과 같은 규칙**(07-21 결정): `Target=null` + `ManualMove=true` + `AbandonWork()` + `ExitCombat()`. 안 그러면 전투가 목적지를 덮어쓰거나 도착하자마자 일하러 간다.
- **전원 도착 후 일괄 출발.** 한 명씩 빼면 "누구는 갔고 누구는 걸어가는 중"인 중간 상태가 생겨 취소 범위가 애매해진다. 대신 한 명이 못 오면 막히므로 **[취소]로 언제든 푼다** — 아직 아무도 안 떠났으니 되돌릴 게 없다.
- 편성 중 죽거나 사라진 폰은 조용히 명단에서 빠진다(그것 때문에 출발이 막히면 안 된다).

### 2. 밟은 함정 둘
- **하수인은 이동 명령이 안 먹었다.** `ManualOrderNode`가 **방랑자 트리에만** 있어서, 하수인은 `SetMoveTarget`을 걸어도 다음 틱에 작업/순찰이 목적지를 덮어썼다. → 하수인 트리 맨 위에 같은 노드를 넣었다. 우클릭 이동은 여전히 방랑자 전용이므로(`MoveController`) 하수인에 `ManualMove`를 세우는 건 원정 편성뿐이다.
- **먼저 도착한 폰이 다시 일하러 갔다.** `ManualOrderNode`는 목적지가 소진되면 명령을 자동 해제한다(그 해제가 없으면 한 번 명령한 폰이 영영 일을 안 하므로 옳은 동작이다). 그래서 "도착했지만 계속 대기"를 표현할 수 없었다. → `UnitBlackboard.HoldPosition` 신설 + `ManualOrderNode` 맨 앞에서 검사. 푸는 건 명령을 건 쪽(취소/출발) 몫이다. `PawnStatusText`에 "집결 대기" 추가.

### 3. `ExpeditionPanel`(G키) + `ExpeditionRowUI`
- 플레이어 폰 목록(체크박스), 줄마다 **`적재 +N`** 표시 — 적재는 근력에서 나오므로(`Strength × 5`) 누구를 데려갈지의 판단 근거다. 기절한 폰은 목록에서 빠진다.
- 하단에 `선택 3명 · 적재 210` 요약 + 상태줄. 집결 중엔 **목록을 잠그고** `핵 앞으로 모이는 중 2/3`을 보여준다(걸어가는 중에 명단이 바뀌면 누가 가는지 흔들린다).
- 순서는 로스터·무리 관리와 동일(방랑자 → 하수인, 이름순).
- 출발이 끝나면 월드맵으로 자동 전환되고, 패널은 `OnModeChanged`로 닫힌다 — 안 닫으면 돌아왔을 때 이미 떠난 폰들의 낡은 목록이 보인다.

### 검증 필요
1. G → 패널이 열리고 플레이어 폰이 전부 보이는지. 체크할 때 요약의 인원·적재가 맞는지.
2. [출발] → 고른 폰들이 **핵 앞으로 걸어가는지**(하수인 포함). 하던 작업·전투를 놓고 오는지.
3. 먼저 도착한 폰이 **그 자리에 서서 기다리는지**(다시 일하러 가지 않는지). 로스터 상태가 "집결 대기"인지.
4. 전원 도착 → **함께 사라지고 월드맵으로 전환**되는지. 파티 토큰이 커지는지.
5. 집결 중 [취소] → 폰들이 **하던 일로 돌아가는지**(대기 상태로 굳지 않는지).
6. 원정 후 거점 복귀 → 폰들이 정상적으로 되살아나 일하는지(`HoldPosition`이 풀려 있는지).
7. 집결 중 한 명이 못 오는 상황(길 막힘/기절)에서 [취소]로 빠져나올 수 있는지.

## 2026-07-30 (6) — 자원 지대 채집: 원정대 등짐 + 바이옴 게이팅을 처음으로 실제로 쓴다

도착 메뉴에 "준비 중"으로 잡아둔 자리 셋 중 **채집**을 먼저 채웠다. 필드맵 생성이 필요 없어 월드맵 안에서 완결되고, `BiomeContentData`(설계 step 7)를 처음으로 실제 게임 동작에 쓰며, 원정대에 "누구를 데려가나"라는 선택을 만들어 준다.

### 1. `ExpeditionParty.Cargo` — 등짐
- **적재 한도 = 멤버 근력 합 × 5.** 필드 폰의 적재 규칙(`CombatHandler` / `PawnMover`의 `Strength * 5f`)과 **같은 식**이다 — 원정대만 다른 규칙을 쓰면 "이 폰을 데려가면 얼마나 더 지나"가 계산되지 않는다.
- `TryAdd`는 한도까지만 받고 **실제로 받은 개수를 돌려준다**. 넘치는 만큼 조용히 사라지면 안 된다(07-21의 `Storage.TryAdd` 잔량 증발과 같은 종류의 함정).
- 멤버가 없으면 한도 0 → G키 편성에 비로소 의미가 생긴다.

### 2. 채집 (`WorldMapView.Harvest`)
- 자원 지대 칸에 **도착**하면 메뉴에 [자원을 채집한다]. 그 칸 **바이옴의 자원 풀**(`BiomeContent.ResourceNodes`)에서 하나 추첨 → `DropMin~DropMax` 수량 → 등짐.
- **무엇이 나오는지는 `BiomeContentData`가 정한다** — 코드는 추첨만 한다. 바이옴 게이팅이 드디어 실제로 굴러간다.
- **하루 한 번**(`_harvestedOn`) — 같은 자리를 무한히 긁지 못하게. 날짜는 `GameTimeManager.CurrentDay`(static이다, `Instance.CurrentDay` 아님).
- 못 하는 이유를 **각각 다른 말로** 막는다: "이 지역엔 없음" / "동행 없음" / "오늘은 다 캤다" / "등짐 가득". 왜 회색인지가 버튼에서 읽혀야 한다.
- 메뉴 정보줄에 `등짐 12/40` 상시 표시.

### 3. 거점 진입 시 입고 (`UnloadCargo`)
- 멤버를 되살린 **뒤에** 부른다 — 그래야 창고가 `OnEnable`로 레지스트리에 올라 있다.
- **`FindNearest`를 반복하지 않는다.** 가장 가까운 창고가 가득이면 매번 같은 창고를 다시 집어 남은 양이 갈 곳을 못 찾는다 → 창고 목록을 거리순으로 한 번 정렬해 훑는다. 필터는 `Storage.TryAdd`가 `CanAccept`로 건다.
- 받아줄 곳이 없으면 **등짐에 남기고 경고**한다. 증발시키지 않는다.

### 검증 필요
1. 필드에서 폰 선택 → **G**로 원정대 편성 → M → 자원 지대 칸으로 우클릭 이동 → 도착 메뉴에 [자원을 채집한다]가 **활성**인지.
2. 눌렀을 때 콘솔에 `채집 — <아이템> ×N`이 찍히고 **정보줄의 등짐 수치가 오르는지**.
3. 한 번 더 누르면 **"오늘은 다 캤다"**로 막히는지. 하루가 지나면 다시 되는지.
4. 멤버 없이 갔을 때 **"동행 없음"**, `BiomeContentData`에 자원 풀이 빈 바이옴에서 **"이 지역엔 없음"**이 뜨는지.
5. 거점으로 돌아가 진입 → **창고에 실제로 들어오는지**. 창고를 가득 채워두면 등짐에 남고 경고가 뜨는지.
6. 등짐을 한도까지 채운 뒤 채집하면 **"등짐 가득"**으로 막히는지, 부분 적재 시 `N개 중 M개만` 로그가 맞는지.

## 2026-07-30 (5) — 월드맵 도착 메뉴(마운트앤블레이드식): 가봐야 안다

## 2026-07-30 (4) — 월드맵 이동을 우클릭으로 + **"월드맵을 켜면 필드를 끈다"를 철회**

### 1. 파티 이동 = 우클릭
좌클릭 이동은 필드와 어긋났다(필드에선 좌클릭=선택, 우클릭=이동 명령). `WorldMapView.HandleClick`을 `rightButton`으로 교체 — **좌클릭은 선택/조회 몫으로 비워 둔다**(월드맵 노드 정보 UI가 붙을 자리). 중클릭은 카메라 회전이라 안 겹친다.

### 2. 필드 시뮬 정지 철회 — 거점은 월드맵을 봐도 계속 돈다
07-29에 "필드맵과 월드맵을 동시에 유지하지 않는다"로 정하고 `GameModeManager`가 활성 정착지 루트를 통째로 껐다. **되돌린다.** 사용자가 재검토를 요청해 수치를 다시 계산한 결과, 그 결정의 전제가 성립하지 않았다.

- **명분이 무너졌다.** "월드맵 이동에 시간이 드니 그동안 거점은 오프라인 추상 생산으로"였는데 — 맵 한 변 64유닛(16칸 × `nodeSpacing` 4) ÷ `partySpeed` 5 = **횡단 13초, 대각선 18초**. 하루는 `dayDuration` **3600초**다. 하루 경계를 넘으려면 지도를 200번 왕복해야 한다. **오프라인 추상 생산은 사실상 발동하지 않는 코드**였고, 필드를 끄고 얻는 건 성능뿐, 잃는 건 상태 연속성이었다.
- **추상 방어 판정을 안 만들어도 된다.** 원정 중 습격이 오면 M키로 돌아가 싸우면 된다. 플레이어가 개입 못 하고 주사위로 결판나는 시스템(설계 step 5의 "추상 방어")이 통째로 불필요해졌다 → `EventManager`를 `_fieldOnly` 수집에서 뺐다(월드 모드에서도 계속 돈다).
- **원정 ↔ 거점 운영이 동시에 진행된다.** `ExpeditionParty`는 "일부는 나가고 일부는 남는다"가 전제인데 필드가 멈추면 남은 폰도 멈춰, 던전 코어 운영과 탐험이 배타가 됐다.

### 3. 코드 변경 — 축 하나만 걷어냈다
`GameModeManager.Apply`가 뒤집던 5축 중 **①(정착지 루트 `SetActive`)만 제거**. ②~⑤(루트 밖 필드 전용 컴포넌트 · 필드 UI 캔버스 · 카메라 · 월드 루트)는 어느 설계든 필요하다 — 지도 위에 필드 UI가 뜨거나 WASD가 양쪽에 먹으면 안 되므로.

- **루트 활성화 책임을 `SettlementManager`로 되돌렸다.** `SwitchTo`가 이전 거점을 끄고 대상을 켠다. 한 번에 하나만 시뮬되는 이유는 이제 모드가 아니라 **"활성 정착지는 하나"**라는 규칙이다. `SetFieldSimulated` / `FieldSimulated` 삭제(모드가 부르던 진입점이라 쓸 데가 없어졌다).
- **`TickOfflineProduction`은 코드 변경 없음.** 판정(`Root.activeSelf`)이 그대로 맞아떨어진다 — 활성 거점은 늘 켜져 있어 걸리지 않고, 안 보는 다른 거점만 대상이 된다. **원래 이 장치가 겨냥한 게 그거였다.** 07-29에 판정을 `s == Active` → `Root.activeSelf`로 바꿨던 것이 이 혼선의 증상.
- `LeaveField`(고스트/핵 이전 미리보기 정리)는 유지 — 건설 고스트가 월드맵으로 따라가면 안 되는 건 그대로다.
- **`Setup Settlement Root`는 남기되 긴급도가 내려갔다.** 모드 전환의 전제가 아니게 됐고, 필요해지는 시점은 **거점이 둘 이상**일 때(전환)와 원정대 재부모화(`EnterSettlement`)다. 에디터 스크립트 주석에 명시.

### 4. 재검토 시점 (미리 못 박아 둔다)
① 월드맵 이동이 실제로 며칠 걸리게 되면(속도↓ / 맵↑ — 마운트앤블레이드식 페이싱) 정지 + 추상 생산이 다시 의미를 가진다. ② 폰 수가 늘어 필드+월드 동시 시뮬이 부담되면. **둘 다 완전 정지 말고 "월드 모드에서 필드는 저속 틱"이라는 중간 지점부터 볼 것.**

### 알려진 잔여
- **`EventNotificationUI`가 월드 모드에서 안 보인다** — 필드 캔버스 아래라 캔버스와 함께 꺼진다. 습격이 떨어져도 지도에선 모른다. 월드 측 알림이 필요하다(다음 작업 후보).

### 검증 필요
1. 월드맵에서 **우클릭**으로 파티가 이동하는지. 좌클릭은 아무 일도 안 하는지.
2. M키로 월드맵 → 필드의 폰이 **계속 일하는지**(카메라를 필드로 돌려 확인하지 말고, 돌아왔을 때 작업이 진행돼 있는지로 판단). 시간·성장·건설이 진행되는지.
3. 월드맵에서 WASD/중클릭/휠이 **월드 카메라만** 움직이는지 — 필드 카메라가 같이 안 도는지.
4. 월드맵 중에 습격 이벤트가 떨어지고, M키로 복귀하면 적이 실제로 거점에 와 있는지.
5. 왕복 전환을 여러 번 해도 선택 상태·창고 수량·일감이 정상인지(루트를 안 끄므로 `OnEnable` 재등록 경로 자체가 안 도는 게 정상).

## 2026-07-30 (3) — 월드맵: 칸별 타일 → 이어진 지형 한 장 + 격자 이동 → 자유 실시간 이동

칸마다 땅 조각을 까는 방식은 동작은 했지만 **타일이 보였다**. 원한 건 "전체로 큰 맵". 그리고 이동도 격자 스냅이 아니라 실시간 자유 이동으로.

### 1. 지형 — `WorldMapTerrain`(신규): 맵 전체가 메시 한 장
칸별 타일의 근본 한계는 **가장자리를 0으로 고정해야 이음새가 맞는다**는 것이었다. 그래서 여러 칸에 걸친 산맥이 원리적으로 안 나왔다. 한 장으로 만들면 그 제약이 사라진다.

- 저작한 격자(바이옴 배치)를 **재료로만** 쓰고, 칸 경계에서 끊기지 않는다 — 높이·기복 성격을 이웃 칸끼리 **이중선형으로 섞어** 샘플하므로 숲→산지로 갈수록 능선이 서서히 험해진다.
- **`BiomeTerrain`(신규)** = 바이옴별 지형 성격의 단일 출처. `Base`(기준 표고) / `Amplitude`(기복 크기) / `Roughness`(잘기). 산악은 동굴(7.0), 늪은 꺼짐(-0.8). **지도 모양을 바꾸려면 이 표만 고친다.**
- 기복은 **fBm**(Perlin 3옥타브) — 결정적이라 같은 시드면 항상 같은 지형. `seed`를 바꾸면 바이옴 배치는 그대로 두고 능선만 다시 뽑힌다.
- 색은 칸 해상도 텍스처를 Bilinear로 늘려 경계를 번지게(06-18 "바둑판 아님" 유지). UV는 텍셀 중심이 노드 중심에 오도록 정렬.
- 면마다 정점을 분리한 **플랫 셰이딩** — 타일 때 좋다고 한 각진 로우폴리 느낌을 그대로 가져왔다.
- 정점 수를 보고 `IndexFormat.UInt32` 자동 전환. `MeshCollider`로 표면 샘플·클릭 판정.
- **직접 만든 지형을 쓰는 길은 그대로** — 이 컴포넌트를 빼면 `WorldMapGrid`가 씬의 지형에 레이캐스트한다(둘 다 지원).

### 2. 이동 — 격자 BFS 폐기, 클릭한 지점으로 자유 이동
- `WorldMapView`의 노드 경로 큐·BFS(`FindNodePath`) 삭제. 클릭한 **그 지점**을 목표로 직진하고, 매 프레임 `grid.SurfaceAtWorld`로 지형에 발을 붙인다(`SurfaceAtWorld` 신설).
- `_party.CurrentNode`는 이동 중 위치에서 **계속 역산**된다 — 격자는 이제 이동 제약이 아니라 "지금 어느 지역인가"(바이옴·정착지 판정)를 읽는 논리 레이어일 뿐이다.
- 정착지 진입(Enter)은 이동이 멈춘 뒤에만.

### 3. 정리
- `WorldTileVisualData`에서 `Ground` 제거(칸별 땅 조각이 없어졌다). 남은 건 **데코 + 내용물 마커**.
- **`BiomeTileCreator` 삭제** — 방향이 바뀌어 역할이 사라졌다. 이미 생성된 `3_Prefab/World/`(타일 프리팹·메시)와 `2_Material/World/`(타일 머티리얼)도 **더 이상 쓰이지 않으니 지워도 된다**(사용자 에셋이라 임의로 지우지 않음).
- `WorldMapSceneSetup`이 `WorldMapTerrain`도 보장하도록 추가. 에디터 스크립트 5개.

### 4. 월드맵 카메라도 필드처럼 조작
월드 카메라가 고정이라 지도를 훑어볼 수 없었다. **같은 `CameraController`를 월드 카메라에 붙였다** — 조작감이 필드와 동일하다(WASD 이동 / 중클릭 회전 / 휠 줌). 필드 전용 로직이 없는 범용 컨트롤러라 그대로 재사용된다.

- **`GameModeManager`에 `_worldOnly` 축 신설**. 전에는 모든 `CameraController`를 필드 전용으로 보고 월드 모드에서 꺼버렸다. 이제 분류 규칙은 **"월드 카메라 오브젝트에 붙어 있으면 월드 측"** — 필드/월드가 서로 반대로 켜진다. `worldCamera`가 정해진 뒤에 수집해야 하므로 `Resolve` 순서가 전제.
- 컨트롤러가 시작 시 비활성이라 `Start()`가 미뤄지는데, Unity가 **처음 활성화될 때 호출**하므로 그때 현재 각도로 yaw/pitch를 잡는다 — 별도 처리 불필요.
- **조작감 기준값은 실제로 굴려보고 고른 값**을 박아둔다(`TuneWorldCamera`: 이동 22.4 / 회전 10 / 줌 300 / 피치 30~90 / 높이 30~90). 처음엔 맵 폭으로 계산하는 공식을 썼는데, 사용자가 씬에서 직접 맞춘 값이 더 나아 그걸 기준으로 교체했다. **이미 컴포넌트가 있으면 값을 절대 건드리지 않고**, 현재 값을 로그에 찍어 그대로 두고 있음을 보여준다.
- 이미 컨트롤러가 붙어 있으면 **설정을 손대지 않는다**(직접 맞춘 값 보존).
- **`WorldCameraBounds`(신규)로 맵 밖 이탈 차단.** `CameraController`가 Update에서 움직인 **뒤** 보정해야 하므로 `LateUpdate`(+`DefaultExecutionOrder(50)`). `edgeMargin`(기본 24)으로 가장자리 바깥 여유.
  - **초안이 틀렸다 — "보고 있는 지점"만 가두고 카메라 위치는 안 막았다.** 기울어진 카메라는 초점보다 `높이 ÷ tan(피치)`만큼 뒤에 선다: 피치 30°·높이 90이면 **156유닛 뒤**인데 맵 한 변이 64유닛이라, 초점이 가장자리에 붙어도 카메라는 맵 밖 한참 바깥이었다. "막히긴 하는데 뚫린다"는 피드백의 정체.
  - → **카메라 위치(XZ)를 직접 클램프**로 교체. 말 그대로의 동작이고 예측 가능하다. 기울어진 시점이라 먼 쪽 가장자리 너머가 화면에 들어오는 건 정상(RTS 카메라의 기본 성질).

### 검증 필요
1. `Setup World Map Scene` → Play → M키. **지형이 한 장으로 이어져 보이는지**(칸 경계·타일감이 없는지). 바이옴 색이 번지며 섞이는지.
2. 동굴/용암 지역을 넓게 칠하면 **여러 칸에 걸친 산맥**이 나오는지. 늪이 꺼지는지.
3. 지도 아무 데나 클릭 → 파티가 **그 지점으로 직진**하며 지형 굴곡을 타고 가는지(공중에 뜨거나 파묻히지 않는지).
4. 이동 중 `CurrentNode`가 따라오는지 — 정착지 칸에 도착해 멈춘 뒤 Enter가 먹는지.
5. `WorldMapTerrain`의 `seed`를 바꾸면 능선만 달라지고 바이옴 배치는 그대로인지. `subdivisions`를 올렸을 때 프레임이 견디는지.
6. 월드맵에서 **WASD/중클릭/휠**이 먹는지. 필드로 돌아가면 월드 카메라 조작이 멈추고 **필드 카메라가 정상 복귀**하는지(두 컨트롤러가 동시에 살아 있지 않은지).
7. 카메라를 어느 방향으로 밀어도 **맵 밖으로 안 빠지는지**. 가장자리에서 시점을 낮추거나(PageDown) 회전해도 갇히는지 — 낮은 각도에선 시선이 멀리 나가 더 일찍 막힐 수 있는데, 그게 거슬리면 `edgeMargin`을 키우면 된다.

## 2026-07-30 (2) — 월드맵 지형은 **코드가 만들지 않는다**: 저작한 Terrain 위에 얹히는 격자로 전환

같은 날 (1)에서 고도를 저작 축으로 빼고 그 격자로 지형 메시를 생성했는데, **요구를 잘못 읽은 것이었다.** 원한 건 "코드가 지형을 만들어주는 것"이 아니라 **"내가 Unity에서 직접 만들어 붙인 Terrain 위에 그리드가 얹히는 것"**이었다. 방향이 반대라 (1)에서 만든 메시 생성기·고도 저작을 통째로 걷어냈다.

### 걷어낸 것
- **`WorldMapRenderer` 삭제** — 지형 메시 생성, 고도 이중선형 보간, 바이옴 색 텍스처 굽기 전부.
- **`Node.Height` / `WorldTile.Height` 삭제**, 저작 창의 고도 브러시·고도 명암·[고도 평탄화] 제거. 높이는 이제 지형에서 읽는다.
- `BiomeExt`에서 높이 관련 잔재 정리. 바이옴은 **논리 성격**(콘텐츠 게이팅)일 뿐 생김새와 무관해졌다.

### 새로 — `WorldMapGrid` ("지형은 저작물, 격자는 그 위의 논리 레이어")
하는 일이 셋뿐이다.
1. **좌표 변환** — `SurfacePoint(node)` / `SurfacePoint(u,v)`: 해당 지점 위에서 아래로 레이캐스트해 **저작한 지형의 표면**을 찾는다. Unity Terrain이든 직접 만든 메시든 콜라이더만 있으면 똑같이 잡힌다. 콜라이더가 없거나 레이어가 어긋나면 `Terrain.activeTerrain.SampleHeight` 폴백, 그것도 없으면 원점 높이.
2. **격자선** — 각 선을 칸당 `lineSubdivisions` 조각으로 잘라 표면을 따라가게 만든 **선분 메시 한 장**(`MeshTopology.Lines`). 지형에 착 붙는다. `showGrid` / `SetGridVisible`로 끄고 켠다.
3. **오브젝트 배치** — POI(마을·소굴·자원·정착지)와 바이옴 데코를 표면에 앉힌다. 데코는 흩뜨린 **그 자리의** 표면을 다시 샘플하므로 경사에서 뜨지 않는다.

- `gridOrigin`이 격자 (0,0) 칸의 **모서리**. 여기서 +X/+Z로 `nodeSpacing`씩 뻗는다 → 저작한 지형에 맞춰 원점만 맞추면 된다.
- **격자가 지형 밖으로 나가면 경고**한다(표면을 못 찾은 칸 수를 세서 한 번에). 원점·칸 크기·`terrainMask` 중 무엇이 어긋났는지 바로 알 수 있게.
- 클릭 판정은 지형 콜라이더 → 좌표 환산. `WorldTileRef`는 콜라이더 가진 프리팹 대비 폴백으로만 남았다.

### `Create World Map View`
지형을 만들지 않는다. 카메라·`MapRoot`·`WorldMapGrid`만 구성하고, **로그로 다음 할 일을 알려준다** — 지형을 `MapRoot` 아래에 넣고 좌하단 모서리를 원점에 맞출 것, 콜라이더/레이어 확인, 격자 칸수×간격이 지형 크기와 맞는지.

### 후속 — 메시로 결정 + 바이옴 땅 조각을 코드로 생성
사용자가 모델링 경험이 없어 **메시 노선 + 내가 만들어 준다**로 정리. 손 아트는 못 만드니 **절차 생성 로우폴리**로 대신한다(나중에 모델링한 메시로 갈아끼우면 되고, 배치 코드는 그대로).

- **`WorldTileVisualData.BiomeVisual`에 `Ground` 추가** — 그 바이옴 칸에 깔 땅 조각. 채우면 **타일들이 모여 지형**이 되고, 비우면 씬에 따로 만들어 둔 지형 위에 격자만 얹힌다. **두 방식을 다 지원**한다(`WorldMapGrid`는 어느 쪽이든 표면에 레이캐스트할 뿐이므로).
- **`WorldMapGrid.Build` 2단계로**: ① 칸마다 땅 깔기 → `Physics.SyncTransforms()` → ② 그 표면 위에 POI·데코·격자선. **순서가 뒤집히면 방금 깐 타일의 콜라이더가 아직 물리에 안 잡혀 전부 원점 평면에 붙는다.**
- **`BiomeTileCreator`(신규, `DungeonColony → Create Biome Tile Meshes`)** — 바이옴별 메시/머티리얼/프리팹을 만들어 `WorldTileVisualData.Ground`에 자동 연결.
  - **이음새 규칙**: 가장자리 정점 높이를 0으로 고정(`EdgeFalloff`)하고 안쪽만 변형 → 이웃 타일과 딱 맞물려 칸 경계에 틈·단차가 없다.
  - **플랫 셰이딩**: 면마다 정점을 분리해 각진 로우폴리 느낌. 텍스처 없이 조명만으로 형태가 읽힌다.
  - 바이옴별 성격: 평원=잔물결 / 숲=낮은 구릉 / 사막=한 방향 사구 / 설원=완만한 둔덕 / 용암=날카로운 바위(발광) / 동굴=각진 단 / 늪=가운데가 꺼진 습지. 노이즈는 `Mathf.PerlinNoise`라 **결정적** — 다시 실행해도 같은 타일이 나온다.
  - **에셋은 지우지 않고 내용만 덮어쓴다**(`SaveOrReplace`) — 지우고 새로 만들면 프리팹·SO의 참조가 전부 끊긴다. 반환값은 항상 디스크에 있는 쪽이라 프리팹이 임시 객체를 물지 않는다.
  - 저장 위치는 폴더 규칙대로: 메시/프리팹 `3_Prefab/World`, 머티리얼 `2_Material/World`, SO `5_Data/World`.

### 후속 2 — 배선 메뉴로 통합: `Create World Map View` → `Setup World Map Scene`
씬의 `WorldMapView`가 6월 것이라 `WorldMapGrid`도 없고 `grid`/`visuals` 참조도 비어 있었다. 기존 `Create World Map View`는 **`WorldMapView`를 통째로 지우고 다시 만드는** 방식이라, MapRoot 아래에 지형을 넣어 뒀으면 그것까지 날아간다 — 이제 그게 실제 위험이 됐으므로 폐기했다.

- **`WorldMapSceneSetup`(신규, `Setup World Map Scene`)** — **없는 것만 채우고 참조만 잇는다. 아무것도 지우지 않는다.** WorldMap · SettlementManager · GameModeManager · WorldMapView · MapRoot · WorldCamera · WorldMapGrid를 순서대로 확인/생성하고, `WorldMapData`·`WorldTileVisualData` 에셋도 자동 연결.
- **에셋 자동 연결은 "딱 하나일 때만"** — 여러 개면 고르지 않고 개수만 알린다. 어느 것이 맞는지는 저작자만 안다.
- **이미 있는 카메라는 위치를 안 건드린다**(직접 맞춘 구도 보존). 새로 만들 때만 프레이밍.
- **정합성 검사**: `WorldMapGrid.nodeSpacing`과 타일 한 변(`BiomeTileCreator.TileSize`)이 다르면 경고 — 다르면 타일 사이에 틈이나 겹침이 생긴다.
- 무엇을 생성/확인/연결했는지 **한 줄씩 로그로** 찍는다. 여러 번 실행해도 안전하고, 배선이 끊길 때마다 돌리는 **복구 도구**로 남긴다.
- `WorldMapUICreator` 삭제. 에디터 스크립트는 6개.

**한계(알고 있을 것)**: 가장자리가 0으로 고정이라 **지도가 전체적으로는 평평하다** — 칸마다 국소적인 기복만 생기고 여러 칸에 걸친 산맥은 안 나온다. 산맥이 필요해지면 ① 칸별 고도를 다시 도입해 타일을 그 높이에 배치하거나(가장자리 단차는 스커트로 가림) ② 큰 지형 메시를 따로 만들어 (b) 방식으로 쓰면 된다. 지금은 눈으로 보고 판단할 수 있는 상태를 먼저 만드는 게 목적.

### 지형을 Unity Terrain으로 할지 메시로 할지 (결론: 메시)
`WorldMapGrid`는 **콜라이더에 레이캐스트할 뿐**이라 TerrainCollider든 MeshCollider든 동일하게 동작한다 — 나중에 갈아끼워도 코드 변경이 없다. 그래서 급한 결정은 아니지만, 판단 재료는 정리해 둔다.

- **`Terrain.activeTerrain` 충돌(실제 위험).** 이건 씬에서 **활성화된 첫 Terrain 하나**를 돌려주는 전역 조회이고, 필드맵의 `MapManager.SampleGroundHeight`가 이미 여기에 의존한다(`HierarchicalPathfinder`·`EventManager`도). 월드맵까지 Unity Terrain이면 씬에 Terrain이 둘 — 플레이 중엔 모드 분리로 한쪽만 활성이라 대체로 맞게 풀리지만 **에디터에선 둘 다 활성**이라 건물 배치 미리보기가 엉뚱한 Terrain을 샘플할 수 있다. → **Terrain은 필드맵 전용으로 못 박는 쪽이 안전하다.**
- 월드맵은 멀리서 기울여 보는 **양식화된 미니어처**에 가깝다. Terrain은 높이맵이라 절벽·오버행 같은 실루엣을 못 만드는데, 그 실루엣이 인상의 절반이다.
- Terrain의 강점(스플랫 페인팅·디테일 잔디·LOD)은 **그 위를 걸어다닐 때** 값어치를 한다. 월드맵 위를 움직이는 건 추상 토큰 하나뿐이다.
- 반대로 **모델링 파이프라인이 없으면** Terrain이 당장 굴러가는 결과를 준다. 실용적 순서는 Terrain으로 형태를 잡고 → 마음에 드는 실루엣이 나오면 메시로 대체.

**조치**: `WorldMapGrid`의 Terrain 폴백을 `Terrain.activeTerrain`(전역) → **직렬화 필드 `fallbackTerrain`**(명시적 연결)으로 교체했다. 어느 쪽을 고르든 월드 측이 전역 조회에 기대지 않게 된다.

### 검증 필요
1. Unity Terrain을 만들어 `MapRoot` 아래에 넣고 좌하단을 원점에 맞춤 → Play → M키. **격자선이 지형 기복을 따라 붙는지**, POI가 표면에 앉는지.
2. 지형 밖으로 격자가 삐져나가면 경고가 뜨는지. `terrainMask`를 지형 레이어로 좁혀도 동작하는지.
3. 지형 클릭이 정확한 칸을 고르는지(경사면 포함). 파티 토큰이 표면을 타고 가는지.
4. `showGrid`를 꺼도 오브젝트·이동이 그대로인지.
5. 지형이 아예 없을 때(콜라이더도 Terrain도 없음) 원점 평면으로 떨어지며 경고만 나는지 — 죽지 않는지.

## 2026-07-30 — (폐기된 방향) 고도 저작 + 지형 메시 생성

**아래는 같은 날 (2)에서 되돌린 작업이다.** 기록으로만 남긴다 — "격자에서 지형을 만들어낸다"는 전제 자체가 요구와 반대였다.

07-29의 3D 렌더는 **"바이옴 = 높이"** 였다. `BiomeExt.MapHeight()`에 바이옴별 상수를 박아두고 그만큼 솟은 박스를 세우는 방식이라, 결과는 **계단식 블록 보드**였고 평원 한복판에 언덕 하나를 놓을 방법이 없었다. 사용자가 원한 건 "진짜 3D 월드 지도 + 그 위에 격자로 나오는 오브젝트"라 방향이 반대였다.

### 1. 고도를 바이옴에서 떼어냈다
- `WorldMapData.Node.Height` / `WorldTile.Height` 신설 — **바이옴과 무관한 독립 축**. 지형 종류와 고도가 따로 노는 건 마운트앤블레이드도 마찬가지다.
- **`BiomeExt.MapHeight()` 제거.** 높이를 만들어내는 출처가 둘이면 저작한 값이 언제 이기는지가 흐려진다. `WorldTileVisualData`의 `Height` 오버라이드도 함께 삭제.
- 새 맵은 **완전히 평평하게** 시작한다(전부 고도 0). 절차 생성을 안 하기로 한 방침과 같은 이유 — 지형은 칠해서 만든다.

### 2. 블록 타일 → 연속 지형 메시
- 노드당 `subdivisions`(기본 4)칸으로 잘라 정점 격자를 만들고, 각 정점 높이 = 주변 **노드 고도의 이중선형 보간**. 고도는 노드 *중심*(i+0.5)에 정의돼 있어 색인할 때 0.5를 뺀다. → 칸 경계에 단차가 없다.
- 색은 노드 해상도 텍스처를 구워 **Bilinear로 늘린다** — 칸 경계가 번져 바둑판이 아니라 지도처럼 보인다(2026-06-18 "바둑판 아님" 결정을 3D에서도 유지). UV는 텍셀 중심이 노드 중심에 오도록 정렬해 색이 칸과 어긋나지 않게 했다.
- 메시 한 장 + `MeshCollider`. 큰 맵은 16비트 인덱스 한계(65535)를 넘으므로 정점 수를 보고 `IndexFormat.UInt32`로 전환.
- 노드별 타일 오브젝트가 사라졌으므로 클릭 판정은 좌표 역산으로 돌아왔다(`WorldTileRef`는 콜라이더 있는 프리팹 대비 폴백 경로로 유지).

### 3. 격자는 "오브젝트 배치 레이어"로만 남는다
화면에 격자가 드러나는 건 이제 **그 위에 얹는 것들**뿐이다.
- POI(마을·소굴·자원·정착지)는 지형 표면 높이에 앉는다.
- **바이옴 데코**(`WorldTileVisualData.BiomeDecor`) 신설 — 그 바이옴 칸에 세울 프리팹 + `Density`(몇 할에 세울지) + `Scatter`(칸 중심에서 흩뜨릴 반경) + `RandomYaw`. 프리팹을 안 꽂으면 아무것도 안 세운다(지형만으로 지도가 성립하고, 데코는 아트가 생겼을 때 얹는 층).
- 데코 난수는 **노드 좌표 해시 기반**이라 재생성해도 배치가 흔들리지 않는다. `Scatter`를 0으로 두면 정확히 칸 중앙 — 격자를 일부러 드러내고 싶을 때.
- 흩뜨린 자리의 지형 높이를 다시 샘플해 앉힌다(칸 중심 높이를 쓰면 경사에서 뜬다).
- `WorldTileVisualData`의 성격이 "타일 블록 정의" → **"격자 위에 세우는 오브젝트 정의"**로 바뀌었다.

### 4. 저작 창에 고도 브러시
- 브러시 4종으로: 바이옴 / **고도** / 내용물 / 시작 노드. 고도 브러시는 슬라이더 값(-4~20)을 그 칸의 고도로 **지정**한다(상대 증감이 아니라 지정 — 바이옴 칠하듯 영역을 칠하는 방식).
- **격자에 고도를 명암으로 얹었다** — 색은 바이옴, 밝기는 높이(현재 최저~최고 구간으로 정규화). 2D 창에서도 지형 기복이 읽힌다.
- [고도 평탄화] 버튼 + 상태줄에 그 칸의 고도와 전체 고도 범위 표시.

### 검증 필요
1. 고도 브러시로 언덕을 칠하고 [씬에 연결] → Play → M키로 **부드럽게 이어진 지형**이 나오는지(칸 단차가 안 보이는지). 바이옴 경계 색이 번지는지.
2. 지형 클릭이 정확한 노드를 고르는지(경사면에서도). 파티 토큰이 지형 표면을 타고 가는지.
3. 기존 `WorldMapData.asset`은 `Height` 필드가 없던 시절 것이라 **전부 고도 0 = 완전 평지**로 뜬다. 정상이며, 칠하면 된다.
4. `WorldTileVisualData`에 나무 프리팹을 꽂고 `Density`/`Scatter`를 조절 → 숲 칸에만 흩뿌려지는지, 경사에서 떠 있지 않은지.
5. 큰 맵(예: 64×64, subdivisions 4)에서 프레임/정점 수가 감당되는지(UInt32 전환 확인).

## 2026-07-29 — 필드맵/월드맵 배타 전환: 한쪽이 켜지면 반대쪽은 통째로 꺼진다

사용자 결정: **필드맵과 월드맵을 동시에 유지하지 않는다.** 기존 `WorldMapView`는 M키로 카메라와 `mapRoot`만 토글해서, 월드맵을 보는 동안에도 **필드는 그대로 돌고 있었다** — 폰이 일하고, 시간이 가고, 습격이 떨어지고, 필드 UI가 지도 위에 떠 있었다. "전환형"이라는 설계 이름과 실제 동작이 어긋나 있던 지점.

### 왜 Unity 씬 분리가 아닌가
씬 Single 로드는 싱글톤(`MapManager`/`JobManager`/`DungeonCoreManager`…)을 전부 파괴해 **세이브 시스템이 전제**가 된다. 세이브는 아직 없다. 같은 씬에서 **루트 단위로 끄면** 결과는 같고 상태는 메모리에 그대로 남는다 (설계 `design_world_field.md` 2026-06-20 "씬 전략 = A" 확정 사항과 일치).

### 추가 — `GameMode` / `GameModeManager`
`GameMode { Field, World }` 두 모드가 배타적. `Current` / `IsField` / `IsWorld` / `SwitchTo` / `Toggle` / `OnModeChanged`.

전환 시 다섯 축을 한꺼번에 뒤집는다:
1. **필드 시뮬** — `SettlementManager.SetFieldSimulated(field)` → 활성 정착지 루트 `SetActive`. 이게 핵심이다. 루트가 꺼지면 그 아래 유닛 BT·작업·건물과 레지스트리 등록(`Storage`/`Bed`/`Faction`/`PawnMover`/`FarmPlot`/`PlacedBuilding` — 전부 `OnEnable`/`OnDisable` 대칭)이 통째로 빠진다.
2. **루트 밖 필드 전용 컴포넌트** — `CameraController`·`SelectionManager`·`SelectionBox`·`MoveController`·`BuildModeManager`·`EventManager`. 정착지 루트 밖(씬 루트)에 있어 루트 토글로는 안 꺼지므로 `enabled`를 직접 뒤집는다. 타입으로 자동 수집 — 인스펙터 배선 불필요.
3. **필드 UI 캔버스** 통째로 `SetActive` (모든 `*_UI` 패널의 공통 부모).
4. **카메라** 필드/월드 교대.
5. **월드 루트**(`mapRoot`) `SetActive`.

- **떠나기 전 정리**(`LeaveField`): `CoreRelocator.Cancel()` + `BuildModeManager.Deactivate()`(신설 public 진입점) — 건설 고스트/이전 미리보기가 월드맵 위로 따라가지 않게. 필드 루트를 끄기 **전에** 부른다(그 뒤엔 오브젝트가 비활성이라 정리 코드가 안 돈다).
- **선택 상태는 유지** — 선택된 폰은 루트와 함께 꺼졌다가 돌아오면 그대로 선택돼 있다. 전환할 때마다 선택이 풀리는 게 더 불편하다는 판단.
- **월드 뷰가 없으면 전환 거부** — `mapRoot`/`worldCamera` 둘 다 없는데 필드를 끄면 아무것도 안 보이는 검은 화면이 된다.

### 시간 축 — 오프라인 생산 판정 기준 교정
필드 시뮬이 멈춘 동안에도 `GameTimeManager`는 계속 흐른다(월드맵 이동에 시간이 든다). 그러면 그 정착지는 **노동은 멈췄는데 날짜만 가는** 상태가 된다.
- `SettlementManager.TickOfflineProduction`의 판정을 `s == Active`(활성 정착지냐) → **`Root.activeSelf`(지금 실제로 시뮬되고 있냐)** 로 교체. 월드맵을 보는 동안엔 활성 정착지도 오프라인 추상 생산 대상이 된다.
- 전역 매니저 중 `Update`를 도는 건 `GameTimeManager`뿐임을 확인(`HierarchicalPathfinder`·`JobManager`·`DungeonCoreManager`는 이벤트/조회 전용) → 월드 모드에서 필드는 정말로 조용해진다.

### `SettlementManager` — 루트 활성화 책임 이전
`SwitchTo`가 대상 루트를 **켜지 않는다**. 모드가 배타적이므로 월드맵을 보는 중엔 켜진 필드가 있어선 안 된다. 활성화는 필드 모드 진입 시 `GameModeManager`가 한다(현재 모드가 필드면 즉시).

### `WorldMapView` — 뷰 전환 책임 이전
`SetActiveView`(카메라/루트 직접 토글) 제거 → `GameModeManager.Toggle()` 요청만. `_active`/`_fieldCamera` 필드도 제거되고 `GameModeManager.IsWorld`를 본다. 초기 상태 적용도 `GameModeManager.Start` 한 곳으로 — 두 곳이 다투지 않게.
- `WorldCamera`/`MapRoot` 프로퍼티 노출 → `GameModeManager`가 배선 없이 집어간다(월드 측 참조의 단일 출처).
- M키를 누른 프레임엔 반대편 입력을 처리하지 않고 즉시 반환.
- `EnterSettlement` 순서 교정: 거점 지정 → **필드 모드 전환** → 멤버 복귀. 필드가 켜진 뒤에 되살려야 스폰 위치가 유효하다. 멤버를 **대상 거점 루트로 재부모화**하는 것도 추가 — 안 옮기면 출발 거점 루트가 꺼질 때 원정대가 같이 사라진다(거점이 둘 이상일 때 드러날 버그였다).

### 에디터 — `DungeonColony → Setup Settlement Root`
모드 전환은 "정착지 루트를 통째로 끈다"에 의존하는데, **씬에 그 루트가 없었다**(`SettlementManager.settlements: []`, 필드 오브젝트가 씬 루트에 흩어짐). 그래서 구성 메뉴를 만들었다.
- 씬 루트를 훑어 **전역이 아닌 것 전부**를 `Settlement_0` 아래로 이동 + `settlements[0]`에 연결 + `WorldMap.startNode`와 노드 좌표 동기화 + `GameModeManager` 부착.
- 분류 규칙은 **전역 화이트리스트**(월드 측 / 매니저 / Canvas / EventSystem / Camera / Light / 입력·건설). 새로 만드는 씬 오브젝트는 대개 필드 것이므로 "기본값 = 필드"가 맞다. `DungeonCoreManager`는 전역에 남긴다 — `Awake` 싱글톤이고 `Update`가 없어 꺼서 얻을 게 없다.
- `Undo` 지원 + **이동/유지 목록을 로그로 출력**해 눈으로 검수할 수 있게 했다(자동 분류를 믿고 넘기지 않도록).

### 검증 필요 (Play Mode)
1. `Setup Settlement Root` 실행 → 로그의 이동/유지 목록이 타당한지. 씬 저장 후 Play가 종전과 동일한지(**회귀 우선** — 정착지 루트가 생겼을 뿐 아직 아무것도 안 꺼진 상태).
2. M키 → 필드가 **완전히 정지**하는지: 폰이 안 움직이고, 작업이 안 돌고, 필드 UI가 사라지고, WASD/좌클릭/우클릭이 필드에 안 먹는지.
3. M키로 복귀 → 폰이 하던 일을 이어서 하는지. **창고 집계·침대 점유·팩션 목록이 복구되는지**(레지스트리가 `OnEnable`로 재등록되는 경로 — 이번에 처음 실제로 도는 코드다).
4. 건설 모드/핵 이전 모드 중에 M을 눌러도 고스트·미리보기가 월드맵에 남지 않는지.
5. 월드맵에서 하루가 지나면 그 거점이 **오프라인 생산**으로 자원을 받는지(`OfflineYield` 설정 필요).
6. 정착지 위에서 Enter → 필드 복귀 + 원정대 멤버가 코어 앞에 스폰되는지.
7. 전환을 여러 번 왕복해도 중복 등록/누수가 없는지(창고 수량이 튀거나 일감이 두 번 잡히지 않는지).

### 알려진 잔여 (이번 범위 밖)
- `JobManager._jobs`는 전역 리스트라 정착지가 둘 이상이면 남의 거점 일감이 섞인다. 지금은 시뮬되는 맵이 하나뿐이라 무해(`IsSiteUsable`이 휴면 건물을 거른다). 다중 정착지 진입 시 정리 필요.
- `BuildingBlueprint.All`은 `Start`/`OnDestroy` 등록이라 루트가 꺼져도 목록에 남는다. 청사진이 있는 채로 전환할 때만 문제.

## 2026-07-29 (2) — 월드맵 저작: 랜덤 생성 → 격자에 칠하는 에디터 + 안개 폐기 반영

"세이브 시스템을 만들까, 아니면 월드맵을 에디터로 만들까" → **월드맵 저작 우선**으로 결정.

**세이브를 미룬 이유**: 직렬화는 데이터 모델이 굳은 뒤에 붙여야 하는데 최근 작업 우선순위·이동·로스터가 연달아 갈아엎였다. 지금 만들면 스키마를 계속 다시 쓰게 된다. 게다가 월드 레이아웃은 **세이브 데이터가 아니라 저작 데이터**라, 월드맵 저작이 오히려 세이브 설계의 선행 조건이다.

### 추가 — `WorldMapData` (SO, `Create → DungeonColony → WorldMapData`)
저작된 월드맵 한 장. `Width`/`Height`/`StartNode` + `Node{Biome, Content}` **행 우선 1차원 배열**(Unity는 2차원 배열을 직렬화하지 못한다).
- `Resize(w,h)` — 좌하단 기준으로 기존 내용 보존.
- **`builtWidth`/`builtHeight`(숨김 필드)로 "배열이 어느 크기로 지어졌는지"를 따로 기록.** `Width`/`Height`만 보고 옛 크기를 추론하면, 인스펙터에서 크기를 고치는 순간 그 값이 이미 새 값이라 **저작한 지도가 통째로 날아간다**. 구현 중 실제로 그렇게 짜여 있어 고쳤다.
- `Fill` / `ClearContent` — 밑칠 도구. `OnValidate`가 크기 불일치를 복구.

### `WorldMap` — 저작한다, 생성하지 않는다
`mapData`가 연결돼 있고 배열 크기가 맞으면 그대로 싣는다(크기·시작 노드도 **데이터가 이긴다**).
- 저작 맵에 찍힌 `MySettlement` 노드는 전부 내 거점으로 등록. 시작 노드는 어떤 경로로 왔든 반드시 정착지가 된다(`SettlementManager.settlements[0]`이 여기 앉으므로).
- **절차 생성 경로를 전부 제거**했다(`seed` 필드·`RandomBiome`·`RandomizeBiomes`). 데이터가 없으면 **빈 맵(전부 미지정) + 경고** — 조용히 아무 지도나 만들어내지 않는다. 사용자 지적: 저작 도구를 만들면서 기본값이 랜덤이면 앞뒤가 안 맞는다. 초안은 [새로 만들기]가 랜덤으로 채운 지도를 내놓고 `WorldMap`도 데이터가 없으면 랜덤 생성으로 빠졌다.
- 시작 노드가 범위 밖이면 경고.

### 안개(fog) 폐기 — 06-20 결정을 코드에 반영
설계는 2026-06-20에 "월드맵 전부 보이게"로 정해졌는데 `WorldTile.Discovered` + 어두운 텍셀 처리가 그대로 남아 있었다(코드-설계 갭). **저작한 지도가 어두워서 안 보이면 저작 자체가 무의미**하므로 이번에 같이 걷어냈다.
- `WorldTile.Discovered` / `Discover()` / `IsDiscovered()` 삭제. `WorldMapView`의 어두운 텍셀·발견 시 갱신·POI 은닉도 제거.
- 발견의 긴장은 콘텐츠 은닉이 아니라 **거리 + 위험도 게이팅**("보이지만 못 감")이 담당한다는 원래 결정대로.
- `Biome.Unknown` 주석을 "미발견(안개)" → "미지정"으로 정정.

### 색을 단일 출처로 — 에디터 미리보기 = 게임 지도
`WorldMapView` 안에 private으로 있던 `BiomeColor`/`ContentColor`를 **`BiomeExt.Color()` / `WorldNodeContentExt.Color()`** 확장 메서드로 옮겼다. 런타임 지도면과 에디터 격자가 같은 값을 읽으므로 **저작 화면 색 = 게임 색**이 구조적으로 보장된다. 색을 바꾸려면 확장 메서드 한 곳만 고친다. (`WorldNodeContentExt`에 `DisplayName`/`Symbol`도 함께.)

### 에디터 — `DungeonColony → World Map Editor`
격자에 칠하는 저작 창(`EditorWindow`).

- 도구: 크기 변경(내용 보존), 칸 크기 슬라이더, 전체 채우기(밑칠), 내용물 지우기. **랜덤 도구 없음.**

### 3D 렌더 레이어 — 평면 지도 텍스처 → 타일 지형 (설계의 로직/렌더 분리)
사용자 확인: **격자 창은 로직 레이어 저작으로 그대로 두고, 그 위에 3D 렌더를 얹는다.** 설계 06-20의 "월드맵 표현 = 3D 타일 지형 지향, 로직(WorldTile 그리드)과 렌더(바이옴→지형)를 분리"가 정확히 이 구조.

- **`WorldMapView` = "무엇을 하는가"** — 입력(M/클릭/Enter/G), 파티 토큰, 거점 진입만 남았다. 평면 Quad·`Texture2D`·POI 큐브 생성 코드는 전부 렌더러로 이관.

- **클릭 판정을 좌표 역산에서 타일 표식으로** — `WorldTileRef`가 타일에 자기 노드 좌표를 들고 있어, 타일이 프리팹(경사·불규칙 형상)으로 바뀌어도 판정이 어긋나지 않는다. 표식이 없으면 평면 역산으로 폴백.
- **머티리얼은 색당 1장 캐시** — 노드마다 새로 만들면 16×16만 해도 256장이 뜬다.

## 2026-07-28 — 무리 관리 패널: 우선순위 숫자 폐기(on/off) + 전투 성향 인게임 전환

전투 성향은 코드 API(`SetStanceOverride` 등)만 있고 UI가 없었다. 붙일 자리를 찾다가 기존 `PriorityPanel`(P키)의 문제가 같이 드러나서 한 패널로 합쳤다.

### 발견 — 우선순위 숫자의 절반이 아무 효과가 없었다
사용자 지적("돌 같은 건 직접 배치해서 하는 건데 채굴이 왜 우선순위냐")을 확인해보니 실제로 그랬다.
- **`MineJob`은 어디서도 생성되지 않는다**(죽은 코드). 채굴/벌목은 `ResourceNodePanel`의 [배정] → `Blackboard.AssignedNode` → `WorkNode.TickAssigned` 경로로만 돈다.
- `JobCategory.Logging`·`Guard`는 대응 Job 클래스 자체가 없다.
- → 우선순위 패널의 9개 카테고리 중 **실제로 큐를 타는 건 5개**(건설/농사/제작/연구/운반). 나머지 칸은 조절해도 아무 일도 일어나지 않았다.

### 결정 (사용자)
- 폰별 설정은 **숫자 1~5 폐기, on/off 체크만**. 무엇을 먼저 할지는 **열 순서 = 전역 고정 우선순위**.
- 채굴/벌목/순찰은 토글이 아니라 **현재 배정 상태**로만 표시(직접 배정 방식 유지).
- 관리 대상은 **방랑자 + 하수인 전체**를 한 표에서.
- 이름: `ColonyPanel` / "무리 관리" / P키 유지.

### 추가 — `JobCategoryInfo` (큐/직접배정 구분의 단일 출처)
- `QueueOrder[]` = 건설 → 농사 → 제작 → 연구 → 운반. **배열 순서가 곧 전역 우선순위.**
- `Weight(category)` — 점수 가중치(앞일수록 큼), 큐 밖은 0 = 배정 제외. `DirectAssign[]`, `DisplayName()`.
- 새 Job의 카테고리를 `QueueOrder`에 안 넣으면 그 일감은 아무도 집지 않는다(주석으로 명시).

### 교체 — `UnitPriorities`/`PriorityManager` → `WorkSettings`
- `WorkSettings`(`UnitBrain.Work`) — 끈 카테고리만 저장하는 on/off. `IsEnabled`/`SetEnabled`/`Toggle`/`OnChanged`.
- **하수인도 개체별 설정을 갖는다**: 전에는 `MinionData.AllowedJobs`(SO 공유)로 필터돼 같은 종류 하수인을 따로 굴릴 수 없었다. 이제 SO 값은 **초기값**으로만 쓰고 이후는 개체별.
- `JobManager.RequestJobFiltered` 삭제 → `RequestJob(unit)` 하나로 통합. 점수 = `Weight × 100 + job.Priority`.
- 전역 `PriorityManager`는 역할이 사라져 **삭제**(폰별 on/off + 전역 고정 순서로 커버).

### 추가 — `ColonyPanel` / `ColonyRowUI` (P키)
행 = 폰, 열 = `이름 | 건설·농사·제작·연구·운반 체크 | 배정 | 성향`.
- **작업 체크박스** — 클릭 즉시 그 폰의 `WorkSettings` 토글.
- **배정 열** — `채굴: 화강암` / `벌목: 목재` / `순찰: 구역명` 표시 + [해제] 버튼(노드·순찰 배정 해제). 직접 배정 작업을 패널에서 "볼 수는 있게" 하되 토글로 착각하지 않도록 분리.
- **성향 열** — 클릭마다 자동 → 교전 → 신중 → 도주 → 자동 순환(`SetStanceOverride`/`ClearStanceOverride`). "자동"은 프로필/역할 기본값을 따른다는 뜻.
- 행 정렬: 방랑자 먼저 → 하수인, 각각 이름순. 하수인 이름은 하늘색. 이름 클릭 = 그 폰 선택.
- 대상은 `Work != null && Faction.IsPlayer` — 로스터/선택과 같은 게이트.
- **열 라벨과 행은 런타임 생성** — `JobCategoryInfo.QueueOrder`에서 파생되므로 카테고리를 늘리면 UI가 따라온다. 열 x좌표는 `ColonyColumns`가 헤더/행에 공유.
- 하단 안내: "왼쪽 열의 작업을 먼저 처리합니다 · 채굴/벌목/순찰은 대상에서 직접 배정" — 고정 순서 모델을 화면에서 설명.

### 에디터 — `DungeonColony → Create Colony Panel`
패널 껍데기 생성 + 필드 연결 + **구버전 `Priority_UI`/`PriorityManager` 씬 오브젝트 자동 제거**(스크립트를 지웠으므로 그대로 두면 missing script로 남는다).

### 후속 — 패널 위 마우스 휠이 카메라 줌으로 새던 것
`CameraController.HandleZoom`이 커서 위치와 무관하게 휠을 먹어, 패널 안에서 굴리면 목록이 스크롤되는 대신 카메라가 줌됐다. → **커서가 UI 위면 줌을 건너뛴다**(`EventSystem.IsPointerOverGameObject`, 클릭 게이트와 같은 방식). 무리 관리뿐 아니라 스크롤 뷰가 있는 모든 패널(스탯·인벤토리·상인·제작 등)에 함께 적용된다.

### 후속 2 — 침대 배정이 아무 일도 안 하던 것: 배정 = 눕기
"침대에 폰을 배정해도 아무것도 없다"는 피드백. `RestNode`는 **혈액 60% 이하 / BloodCap 미복구 / 기능상실 부위**가 있을 때만 작동했고, 그때도 침대 *옆에 서서* 회복만 했다(눕는 표현 자체가 없었음). 멀쩡한 폰을 배정하면 화면상 아무 변화가 없다.
- **배정 = "이 폰은 쉰다"는 명령으로 재정의**: 배정된 침대가 있으면 그리로 가서 눕고, 회복이 끝나도 일어나지 않는다. **해제해야 다시 일하러 간다.**
- 일어나는 조건: 배정 해제 / 허기 60 이하(EatNode 임계 — 누운 채 아사하지 않게 먹고 돌아옴) / 소집·전투·도주 등 상위 분기.
- **눕는 자세**: `Bed.SleepPosition`(렌더러 바운즈 윗면 중앙 + `lieHeight`) / `SleepRotationFrom(approachPos)` — **폰이 다가온 면에 맞춰 네 방향 중 하나**로 눕는다(침대 로컬 ±X/±Z 중 가까운 면, 머리는 들어온 쪽 반대편). 처음엔 침대 yaw 고정이라 어느 쪽에서 와도 한 방향으로만 누워 부자연스러웠다. 프리팹에 `sleepAnchor` Transform을 꽂으면 그 지점·회전으로 고정된다.
- **`PawnMover.SetSleeping`**: 누울 때 `CharacterController`를 끄고 위치를 고정(중력·조향이 돌면 침대에서 미끄러지거나 파묻힌다), 일어날 때는 **눕기 직전 서 있던 자리**로 복귀(침대 콜라이더 위에서 깨어나 끼는 것 방지). `SetMoveTarget`은 자동으로 깨운다.
- **중단 처리**: BT 노드에는 중단 콜백이 없어 휴식이 상위 분기에 밀리면 누운 채 굳는다 → `UnitBlackboard.RestTicked`를 매 틱 리셋하고, 틱 후 `UnitBrain`이 "쉬지 않았는데 누워 있으면" 일으켜 세운다.
- `Bed.TryOccupy` — **같은 유닛의 재점유 허용**. 전에는 전투로 자리를 뜬 뒤 점유가 남아 자기 침대에 다시 못 눕는 상태가 됐다.
- 무리 관리 패널 배정 열에 `휴식: 침대` 표시 + [해제]로 침대 배정도 풀린다. `BedUI` 배정 라벨은 오브젝트 이름 → `UnitName`.

### 후속 3 — 폰이 장애물을 못 피하고 맞대고 굳던 것 (지역 회피 + 접근 지점)
"운반 중 다른 폰이 길을 막으면 서로 맞대고 아무것도 못 한다 / 침대도 옆으로 갈 생각을 못 하고 직선으로만 가서 안 움직인다" 피드백. 원인은 하나다 — **길찾기 그래프는 벽(Wall 레이어)만 안다.** 다른 폰·침대·창고는 그래프에 없으니 경로가 그대로 관통해서 나오고, `CharacterController`가 막히면 `PawnMover`는 같은 방향으로 계속 밀기만 했다(진행 여부를 아무도 안 봤다).

- **조향 단계 회피** (`PawnMover.AvoidNearbyPawns`): `avoidRadius`(1.5) 안 + 진행 방향 앞쪽의 다른 폰에서 벗어나는 성분을 조향에 더한다. 측면 회피는 **항상 자기 기준 오른쪽** — 마주 오는 둘은 서로 반대 세계방향으로 갈라지므로 교착이 대칭적으로 풀린다(우측통행). 폰 목록은 `PawnMover` 정적 레지스트리(물리 쿼리 없음).
  - 교전 상대는 회피 제외(붙어야 때린다), 최종 목적지 근처에서도 회피 해제(도착 지점에 모여야 하는데 계속 밀어내면 아무도 도착 못 함).
- **정체 탈출** (`TrackProgress`/`OnBlocked`): 0.35초마다 실제 이동량이 기대치의 35% 미만이면 막힌 것으로 보고 ① 오른쪽 비켜서기 → ② 반대쪽 + 로컬 재계획 → ③ 전역 경로 재계산 → ④ 정지(BT 재시도). 전에는 이 감지 자체가 없어 영원히 밀었다.
- **접근 지점** (`Bed.ApproachPosition(from)`): 침대 중심을 이동 목표로 주던 것을 **네 면 중 설 수 있고(`IsStandable` + 타일 `IsPassable`) 가장 가까운 쪽**으로 바꿨다. 다 막혔으면 가장 가까운 면으로 폴백. 도착 못 하고 이동이 끝나면(막힘) 접근 면을 다시 고른다. → "침대 위쪽에 붙어서 굳는" 상황이 사라진다.
- 눕는 회전도 이 접근 면 기준이라 사방 접근이 자연스럽게 이어진다.

### 후속 4 — U자 함정: 회피가 진동만 하던 것 → 점유 타일을 그래프에 넣고 우회는 플래너에 맡김
"U자로 둘러싸이면 뒤로 돌아 빠져나가지 않고, 옆으로 좀 돌다가 너무 많이 돌아야 하면 반대로 다시 움직인다"는 피드백. 지역 회피(후속 3)로는 못 푸는 **국소 최소점** 문제였다.

- **진짜 원인**: `LocalGridManager.BakeGrid`가 셀 통행 판정에 **바닥 + `Physics.CheckBox(obstacleLayer)`** 만 썼다. `MapManager`의 **건물 점유 타일(`_occupied`)은 보지 않았다** → 건물이 obstacleLayer(Wall)에 없으면 U자가 플래너 눈에 존재하지 않고, 경로가 직선으로 관통해 나온다. 그러니 반사적 조향만 좌우로 흔들렸다.
- **L1 셀 판정에 점유 타일 추가**. 1m 셀은 정수 좌표 스냅이라 맵 타일과 1:1 → 콜라이더 레이어와 무관하게 건물이 벽으로 인식된다. **U자 우회는 이제 Theta*가 낸다.**
- **메소(2m)는 관대하게**: 셀이 덮는 타일이 **전부** 점유일 때만 차단(`AllOccupiedInCell`). 얇은 벽까지 코스 단계에서 막으면 한 칸 통로가 사라져 경로 자체를 못 찾는다 — 정밀 차단은 L1 몫이라는 기존 원칙 유지.
- **`PathBlockMemory`(신설)**: 폰이 막혔던 자리를 3초간 통행 불가로 기억(전 폰 공유, 자동 만료). 다른 폰처럼 그래프에 없는 동적 장애물도 **재계획 시 플래너가 우회**하게 된다.
- **좌우 번갈이 비켜서기 제거**: 진동의 직접 원인이었다. 이제 ① 오른쪽으로 한 번만 비켜보고 → ② 막힌 자리 기억 + 로컬 재계획 → ③ 기억 + 전역 재계산 → ④ 정지. 원칙은 **"우회는 반사적 조향이 아니라 플래너의 몫"**.
- 막힌 자리를 기억할 때 **목적지 코앞은 제외** — 도착 지점 자체를 막으면 영영 못 간다.

### 후속 5 — 폰이 만든 ㄷ자는 여전히 못 뚫던 것: 다른 폰을 길찾기 그래프에 넣음
후속 4는 **건물**이 만든 ㄷ자를 풀었지만, 막은 게 다른 **폰**이면 그대로였다. 폰은 어느 축에도 안 들어가 있어 플래너가 폰 벽을 관통하는 경로를 계속 냈고, `PathBlockMemory`는 부딪힌 자리를 한 칸씩 사후에 기억하는 방식이라 벽 하나 뚫는 데 여러 번 실패해야 했다.

- **`LocalGridManager.BakeOtherPawns`** — 윈도우 안의 다른 `PawnMover` 셀을 통행 불가로 굽는다. 재계획마다 다시 구우므로 폰이 비키면 곧 반영된다. 폰 목록은 정적 레지스트리(`PawnMover.All`).
- **예외 2곳**: 자기 셀, 목적지 ±1셀. 그 셀이 막히면 `PathGrid.FindPath`가 null을 반환해 직선 폴백으로 되돌아간다(= 밀기만 하던 예전 동작). 창고·작업대처럼 여러 폰이 같은 지점으로 모이는 경우도 이 예외로 살아난다.
- `obstacleLayer`에 유닛 레이어를 넣는 방법은 쓸 수 없다 — 자기 셀까지 막혀 경로가 실패한다(기존 주석의 경고). 그래서 예외를 둘 수 있는 베이크 단계에서 직접 굽는다.
- `FindLocalPath(pos, target, self)` / `FindWindowPath(..., self)`로 호출자를 넘긴다. `self`를 안 주면 종전과 동일(폰 무시).
- 반응 속도: 경로는 재계획 시점에만 갱신되므로, 이미 이동 중에 앞이 막히면 **정체 감지(0.35초 × 2단계 ≈ 0.7초)** 후 재계획에서 우회로가 나온다. 매 프레임 재계획은 윈도우 베이크 비용(40×40 CheckBox) 때문에 하지 않는다.

### 후속 6 — 이동 구조 재점검: 완충장치 걷어내고 치수·판정 기준을 맞춤
후속 3~5는 전부 **완충장치**였다(회피 → 비켜서기 → 차단 기억 → 폰 굽기). 구조를 다시 보니 근본 불일치가 두 개 있었다.

**발견 1 — 폰 지름 = 타일 한 칸.** `1 tile = 1 world unit`인데 폰 `CharacterController.radius = 0.5`(지름 1.0). 타일로 건설하는 게임에서 폰이 칸을 꽉 채운다 → 1타일 복도는 교행 여유 0, 폰 사이 1타일 틈은 물리적으로 통과 불가. 교착의 물리적 근원.

**발견 2 — 그래프가 벽 주변을 과하게 막았다.** `half = 0.45 + agentRadius(0.5) = 0.95` → 벽 타일에 직교로 붙은 셀(벽면까지 0.5m)이 전부 통행 불가. **복도를 3타일로 파야 가운데 한 줄이 걸어진다.** 메소는 `1.4`라 더 심했다.

**발견 3 — 두 기준이 어긋나 있었다.** 후속 4에서 추가한 점유 타일 검사는 인플레이션 없이 정확히 그 타일만 막는데, Wall 레이어는 0.95 부풀린다 → 건물 사이 1타일 틈은 "그래프는 통과 / 실제론 못 낌".

**조치** (사용자 결정: 아군끼리만 통과):
- **같은 레이어끼리 통과** — `PawnMover.Awake`가 `excludeLayers = 1 << layer`. 아군 교착이 원인 채로 소멸, 적과는 충돌 유지(몸으로 막는 전술 보존). `layer == 0`(Default)이면 적용 안 함 — 지면이 섞여 있어 제외하면 바닥을 뚫는다.
- **그래프도 같은 기준** — `BakeOtherPawns`가 `PawnMover.IsBlockedBy`로 거른다. 물리에서 통과하는 상대를 벽으로 구우면 헛돈다.
- **판정을 타일 단위로** — L1 `half = 0.45 + max(0, agentRadius - 0.5)`, 메소 `half = tileSize*0.45 + max(0, agentRadius - tileSize*0.5)`. 반경 부풀림은 **타일보다 큰 에이전트에만** 남는다. 씬의 `agentRadius`(0.5)를 안 건드려도 되도록 공식 쪽을 고쳤다(씬 파일은 사용자가 편집 중일 수 있어 손대지 않음).
- **폰 반경 0.5 → 0.3** (`pawn.prefab`의 CharacterController + CapsuleCollider). 지름 0.6 = 1타일 복도에서 좌우 0.2 여유. 그래프가 1타일 복도를 열어줬으므로 폰이 실제로 들어갈 수 있어야 한다 — 둘 중 하나만 하면 오히려 더 낀다.

**남은 판단**: 1·2가 들어갔으니 sidestep / `PathBlockMemory` / 4단계 에스컬레이션의 역할이 크게 줄었다. 지우지 않고 두되, Play Mode에서 실제로 발동하는지 보고 정리할 것.

**1차 계측 결과** (폰 22, 평시): 10초당 막힘 3~4회가 **전부 1단계(비켜서기)**. 2단계 이상 0회, `PathBlockMemory` 적중 0, 폰 차단 0, 점유 차단 베이크당 4셀(1600셀 중), 베이크 8~60회/10초.
→ 평시에는 1단계만으로 정리되고 나머지 완충장치는 놀고 있다. **단, 그 직전 실행에서 관측된 반복 포기(같은 좌표에서 4단계 → BT 재명령 루프)는 이번에 재현되지 않았을 뿐 해결이 확인된 게 아니다.** 그 상황과 전투 중(적이 근처 = `BakeOtherPawns`가 일하는 조건)을 재현해 보고 판단할 것.

**2차 계측 결과** (폰 19, 적 근처/혼잡): 10초당 막힘 3회 = 비켜서기 2 / **로컬재계획 1** / 전역재계획 0 / 포기 0. 베이크 56회, 회당 차단 셀 = 점유 0, 차단기억 0.3, **폰 10.7**.
→ **정리 판정: 걷어낼 부품 없음.** 각각이 다른 상황을 담당하고 평시 비용은 0에 수렴한다.
- 1단계 비켜서기 = 평시·전투 모두 상시 발동, 가장 값싼 첫 수단.
- 2단계 차단기억+로컬재계획 = 혼잡 시 발동하고 **거기서 해결**(3단계로 안 넘어감). 차단기억이 실제로 경로에 반영된 것도 확인.
- `BakeOtherPawns` = 적이 근처일 때만 10.7셀/베이크. 아군 통과 규칙 덕에 평시 0 → 필요할 때만 비용을 낸다.
- 3·4단계 = 두 번의 측정 모두 0. 안전 밸브로만 유지(4단계가 없으면 무한 밀기).
- 1차 측정에서 보인 병리적 패턴(같은 좌표 반복 포기, 차단기억 154셀)은 이후 재현되지 않음 — 아군 통과 + 타일 단위 판정 + 폰 반경 축소가 근원을 걷어낸 것으로 보인다.

**계측 추가** — `MovementDiagnostics`(+ `MovementDiagnosticsTicker`, 자동 설치). 단계별 발동 횟수와 베이크 차단 셀 수(차단기억/폰)를 세어 10초마다 요약 한 줄. 개별 이벤트는 폰당 1초 1줄로 제한. `DungeonColony → Toggle Movement Diagnostics`로 on/off. **추측으로 지우지 않고 관측으로 정리하기 위한 도구** — 정리가 끝나면 같이 걷어낸다.

### 후속 7 — 전투 중 이동 명령이 씹히던 것: 플레이어 명령을 BT 위로
"싸움이 붙으면 내가 움직이려 해도 다시 싸우러 가버린다" 피드백. 우클릭 이동은 `PawnMover`에만 목표를 주고 **`bb.Target`은 건드리지 않아서**, 다음 틱(0.1초)에 `FightNode`가 `SetMoveTarget(적 위치)`로 덮어썼다. 구조적으로 플레이어 명령이 BT 자동 행동보다 **아래**에 있었다.
- **`ManualOrderNode` 신설** — 방랑자 트리에서 소집 바로 아래(도주·전투·작업보다 위). `bb.ManualMove`가 켜져 있고 아직 이동 중이면 `Running`을 반환해 아래 분기를 전부 막는다.
- **자동 해제**: 도착했거나 길찾기가 포기해 멈추면(`!Mover.HasTarget()`) 플래그를 끄고 `Failure` → 평소 행동 복귀. 이 조건이 없으면 한 번 명령한 폰이 영영 일을 안 한다.
- **`MoveController`**: 바닥 우클릭 = `Target = null` + `ExitCombat()` + `ManualMove = true`(교전 이탈). 적 우클릭 = `Target` 지정 + `ManualMove = false`(공격 명령이 이동 명령을 대체).

### 후속 8 — 이동 명령이 하던 작업도 취소하도록 (+ 취소 경로의 자원·주문 누수 차단)
후속 7에서는 작업을 유지해 "도착하면 하던 일로 복귀"였는데, 사용자 요청으로 **이동 명령 = 작업 포기**로 바꿨다.
- **`UnitBrain.AbandonWork()`** 신설 — 큐 일감 취소 + **노드 직접 배정 해제**. 배정을 남기면 도착하자마자 다시 채굴하러 가서 명령이 안 먹는 것처럼 보인다. `Die()`도 이 경로를 쓰게 통일(죽은 폰이 노드의 배정 목록에 남던 것도 같이 정리됨).
- **취소가 사망 전용에서 일상 조작이 되면서** 기존 취소 경로의 누수가 문제로 승격 → 함께 차단:
  - `CraftJob.OnCancelled` — 재료 환불(기존)에 더해 **주문을 큐에 재등록**. 전에는 취소하면 플레이어 주문이 조용히 사라졌다(재료 부족 경로는 이미 재등록하고 있었으므로 정책 통일).
  - `ResearchJob` — `OnCancelled` 자체가 없어 **소비한 재료가 증발**했다. 환불(연구대에 드롭) + 주문 재등록 추가.
  - `HaulJob` — 창고로 가던 중 취소되면 짐이 **폰 인벤토리에 갇혔다**. 그 자리에 드롭하도록 변경(드롭되면 `GroundHaulJob`이 자동 등록돼 다른 폰이 회수).
- `ConstructionJob`은 이미 `OnJobEnded → TryRegisterJob`으로 즉시 재등록돼 손댈 필요 없었다.
- **침대 배정은 유지** — 그건 작업이 아니라 "쉬는 중"이라는 지속 명령이고 패널에 상태로 보인다(해제 버튼도 있음).

### 후속 9 — 배정 해제 시 UI가 안 갱신되던 것
`ResourceNodePanel.RefreshAssigned()`가 **패널을 열 때와 배정 버튼을 누를 때만** 호출됐다. 이동 명령·사망처럼 패널 밖에서 해제되면 목록이 낡은 채로 남는다(이동 명령이 배정을 푸는 기능이 생기며 드러남).
- **`ResourceNode.OnAssignmentChanged`** static 이벤트 신설 — `Assign`/`Unassign`/`OnDestroy`에서 발행. `ResourceNodePanel`(현재 노드면 목록 재구성)과 `ColonyPanel`(즉시 전체 갱신)이 구독. 폴링에 의존하지 않으므로 앞으로 다른 패널이 생겨도 같은 이벤트만 구독하면 된다.
- `using System;` 추가로 `Random`이 모호해져 `UnityEngine.Random.Range`로 명시(같은 파일에서만 발생).

### 후속 10 — 폰 로스터: 하단 가로 카드 바 → 좌측 세로 목록
"인원이 많아지면 UI를 넘어가고, 색도 지금 만드는 UI와 다르다"는 피드백. 기존은 하단 가로 바(290px)에 110×132 카드를 대기중/작업중 두 그리드로 깔아서, 20명이 넘으면 화면 밖으로 나가고 스크롤도 없었다.
- **좌측 세로 목록**(200×420, 사용자 선택): 한 줄 28px = `[초상화 22px][이름][현재 상태]`. 넘치면 스크롤. 좌측 하단은 `UnitHPUI`가 쓰므로 **상단 기준 고정 높이**로 앉혔다.
- **행 순서 고정**(방랑자 → 하수인, 이름순 — 무리 관리 패널과 동일). 상태별로 묶으면 일하는 폰이 계속 자리를 옮겨 클릭이 어렵다 → 상태는 자리 이동 대신 **우측 텍스트+색**으로 표현.
- **`PawnStatusText`** 신설 — BT는 상태를 밖에 안 내놓으므로 블랙보드에서 역추론(기절/소집/전투/휴식/이동/채굴·벌목/작업 카테고리/순찰/대기). 우선순위를 BT 분기 순서와 맞췄다. 상태별 색도 여기서 정의(툴팁 등 재사용 대비).
- **선택 중인 행은 배경 강조** — 로스터와 실제 선택 상태가 따로 놀지 않게.
- 행은 **런타임 생성**(프리팹 제거). `PawnRosterEntryUI.cs` + `PawnRosterEntry.prefab` 삭제 — 열 구성이 코드 한 곳에만 있게 됐다.
- 색·헤더는 무리 관리 패널과 통일(#0D0D0D 헤더 + 어두운 패널). 제목에 인원수 표시.

**후속 — 배치 비교 후 확정**: "크기가 작다 / 다른 방식도 비교하고 싶다" 요청으로 세 배치(좌측목록 / 하단타일 / 하단카드)를 런타임 전환 가능하게 만들어 비교 → **세로 목록으로 확정**, 나머지 둘과 전환 버튼은 삭제(비교가 끝났으므로 코드에 남길 이유가 없다).
- 이 과정에서 **패널 내부(헤더·스크롤·행)를 전부 런타임 생성**으로 옮긴 건 그대로 유지. 크기 값을 바꾸면 초상화·글자까지 따라 커지려면 한 곳에서 계산하는 게 낫다. 생성기는 빈 껍데기 + 참조 연결만 담당.
- 최종: **우측 하단 모서리에 딱 붙는 340×760**, 행 높이 52(초상화 44 · 이름 폰트 ~19). 초상화·글자 크기는 `rowHeight`에 비례해 자동 산출 — 크기를 키우면 폰도 같이 커진다.

**후속 — 모양은 씬이, 코드는 데이터만 (템플릿 복제)**: "편집 중에 쓰는 걸 런타임에서도 쓰게 해달라"는 요청. 중간에 '미리보기 샘플을 따로 그리는' 방식을 거쳤는데, 그건 **미리보기와 실제가 두 갈래로 갈리는** 구조라 요청과 다르다. 최종은 **템플릿 복제**.
- 생성기가 `Content` 아래 **행 하나(`RowTemplate`)**를 씬 오브젝트로 만든다. 런타임엔 `SetActive(false)`로 숨기고 **그걸 `Instantiate`해서** 목록을 채운다.
- `PawnRosterRowUI`에서 배치 코드를 **전부 제거** — 이제 `Bind`(이름·초상화·상태·클릭)와 `Refresh`만 남는다. 여백·폰트·색·크기는 씬 오브젝트가 갖는다.
- 결과: **편집 중 모양 = 게임 모양**이 구조적으로 보장된다. 행 디자인을 바꾸려면 인스펙터에서 `RowTemplate`을 고치면 되고 코드는 건드릴 필요가 없다.
- 이름 칸은 좌우 **스트레치 앵커** — 패널 폭만 바꿔도 목록이 따라 늘어난다(런타임 폭 계산 코드 제거).
- 이 원칙을 `docs/editor_creators.md`에 "모양은 씬이, 코드는 데이터만" 절로 정리했다. 앞으로 반복 항목 UI는 전부 이 방식.

### 후속 3-b — 패널 스크롤 감도
휠 게이트를 넣고 나니 `scrollSensitivity = 20`이 한 노치에 목록이 통째로 넘어갈 만큼 과했다 → **5**로 조정(생성기 상수).

### 검증 필요 (Play Mode)
0. 침대에 폰 배정 → 침대로 걸어가 **눕는지**. 해제하면 일어나 다시 일하는지. 배고파지면 일어나 먹고 돌아오는지. 적이 오면(하수인) 일어나 싸우고, 끝나면 다시 눕는지. 일어난 뒤 침대에 끼거나 바닥을 뚫지 않는지.
0-b. 침대 한쪽 면만 열려 있을 때 그 면으로 돌아가는지(막힌 면에 붙어 굳지 않는지). 폰 둘이 마주 오면 서로 비켜 지나가는지. 운반 중 다른 폰이 길을 막아도 결국 통과하는지. 전투 시 상대에게 정상적으로 붙는지(회피 때문에 맴돌지 않는지).
0-c. **U자 건물 안에 폰을 넣고** 밖으로 목적지를 주면 입구로 돌아 나오는지(좌우 진동 없이). 건물 사이 한 칸짜리 통로를 여전히 통과하는지(메소 과다차단 회귀 확인 — 이게 막히면 코스 라우팅이 실패한다). 창고·작업대 등 점유 타일 위가 목적지인 작업이 정상 배정·수행되는지.
0-d. **폰들로 ㄷ자를 만들어** 가둔 뒤 밖으로 목적지를 주면 열린 쪽으로 돌아 나오는지(0.7초쯤 뒤 우회 경로가 나와야 함). 여러 폰이 같은 창고로 운반할 때 서로를 장애물로 인식해도 도착은 하는지(목적지 ±1셀 예외 확인). 폰이 많을 때 프레임 저하가 없는지.
0-e. (후속 6) **아군끼리 겹쳐 지나가는지** — 이제 통과가 정상이다. **적과는 여전히 부딪히는지**. 유닛이 바닥을 뚫지 않는지(레이어가 Default인 유닛이 있으면 규칙 미적용 — 프리팹 레이어 점검). **1타일 폭 복도를 통과하는지**(이번 변경의 핵심 목표). 반경 0.3이 시각적으로 어색하지 않은지(선택 클릭 판정도 콜라이더 기준이라 같이 볼 것). 좁은 문틀·모서리에서 긁히며 끼지 않는지.
1. `Create Colony Panel` 실행 → 구버전 우선순위 오브젝트가 사라지고 P키로 새 패널이 열리는지. (씬 저장 필요)
2. 체크 해제한 작업을 그 폰이 더 이상 안 잡는지. 전부 끄면 유휴로 떨어지는지.
3. 열 순서대로 처리하는지 — 건설 일감과 운반 일감이 동시에 있을 때 건설을 먼저 잡는지.
4. 하수인 2기가 **서로 다른 설정**으로 움직이는지(같은 MinionData여도). `AllowedJobs`가 채워진 하수인은 그 값이 초기 체크 상태로 들어오는지.
5. 자원 노드에 배정하면 배정 열에 뜨고 [해제]가 먹는지. 순찰 구역도 같은지.
6. 성향 순환이 실제 행동으로 이어지는지 — 도주로 두면 적을 보고 달아나고, 자동으로 되돌리면 다시 싸우는지. 소집 중에는 도주하지 않는지.
7. 회귀: 방랑자의 기존 작업 흐름(운반/건설/농사/제작/연구)이 그대로인지.

## 2026-07-27 (4) — 팩션 관계 시스템: 세력 SO + 방향별 적대/중립/아군

기존엔 `FactionType {Player, Enemy}` 2분법에 적대 판정이 "타입이 다르면 적"이라, **적끼리·NPC끼리는 절대 안 싸우고** "이 적은 저 NPC와만 안 싸운다" 같은 예외를 표현할 수 없었다.

### 결정 (사용자)
- **데이터 형태**: 세력 SO 하나 = 한 세력. 각 에셋이 `기본 성향 + 상대별 예외 목록`을 들고 있음(단일 매트릭스 X — 마을/무리별로 세력이 늘어나는 구조라 파일 분리가 유리).
- **방향성**: **방향별**. A가 B를 적대해도 B는 A를 중립으로 둘 수 있음(산적→마을사람 선공 / 마을사람→산적 도망).

### 추가 — `FactionData` (SO, `Create → DungeonColony → FactionData`)
- `FactionStance {Ally, Neutral, Hostile}`, `FactionName`, `PlayerControlled`, `DefaultStance`, `Relations[{Other, Stance}]`.
- `StanceTo(other)`: 예외 목록 → (자기 자신 = Ally) → `DefaultStance`. 자기 세력을 매번 적을 필요 없음.
- `Faction` 컴포넌트: `Data`(SO) + **레거시 `factionType` 폴백**. 한쪽이라도 SO가 없으면 기존 Player↔Enemy 규칙으로 판정 → **SO를 안 붙인 기존 씬·프리팹은 동작 그대로**(점진 이행 가능).
- API: `IsPlayer` / `StanceTo` / `IsHostileTo`(선공 여부) / `IsAllyOf`(같은 편).

### 반격 축 (관계와 무관)
방향별 관계는 "중립인데 맞아도 가만히 있음"이 되면 무너지므로 반격을 별도 축으로 넣었다.
- `UnitBlackboard.LastAttacker` + `LastAttackedTime` + `RetaliationMemory`(15초) + `RecordAttacker`.
- `BodyPartSystem.TakeDamage`가 `DamageInfo.Source`를 기록 — **아군 오사는 원한으로 치지 않음**(사격 관통 피해로 아군끼리 싸우는 것 방지).
- `DetectNode`: 주변 탐색보다 **반격 대상 우선**. `NpcFleeNode`: 때린 상대를 위협으로 인식.

### 소비처 이행 — enum 분기 제거
`FactionType.Enemy/Player` 직접 비교를 전부 역할 판정으로 교체(세력이 늘어나도 안 깨지게).
- **`UnitBrain.UsesEnemyAi`** 신설 = `NpcData/MinionData 아님 && !IsPlayer` → **BT 선택**(적 트리) + **사망 시 시체화** + **UnitPriorities 제외** 3곳이 이걸 씀. 기존 Player/Enemy 씬에서는 판정 결과가 이전과 동일.
- `SelectionManager`(선택 2곳) / `PawnRosterPanel` / `UnitBrain.UpdateHunger` → `IsPlayer`.
- `MoveController` 우클릭 타겟팅 → `!IsPlayer`(중립도 플레이어가 조준은 가능 — 선공 결정은 플레이어 몫).
- `SubCore` 범위 효과 → `!IsPlayer`면 피해, 아니면 버프.
- `CombatHandler.HolyAoEHeal` → **아군만** 치유(`IsAllyOf`, 중립 제외). 사격 오사 회피(`FindAllyInLineOfFire`)는 **적대가 아닌 대상 전부** 보호 유지 — 중립을 쏴서 원한 사는 것도 막는 게 맞다고 판단.

### 스타터 에셋 생성기 — `Editor/FactionCreator.cs`
`DungeonColony → Create Starter Factions` → `Assets/5_Data/Faction/`에 4종 생성 + 관계 기입. 방향별 모델의 대표 케이스를 그대로 담아 바로 시험 가능하게 함.

| 에셋 | 기본 성향 | 예외 관계 |
|---|---|---|
| `Faction_Player` (PlayerControlled) | Neutral | 고블린·산적 Hostile / 마을사람 Neutral |
| `Faction_Goblin` (몬스터) | **Hostile**(목록 밖 전부 적) | 없음 — 사람이든 뭐든 다 적 |
| `Faction_Bandit` (사람) | Neutral | 플레이어·마을사람·고블린 Hostile |
| `Faction_Villager` | Neutral(아무도 선공 X) | 플레이어 Ally |

→ 고블린↔마을사람·산적→마을사람이 **일방 적대**(상대는 중립)라 "한쪽만 덤비고 다른 쪽은 도망"이 바로 확인된다. 고블린↔산적은 상호 적대(몬스터 vs 사람). 비공개 `[SerializeField]`는 `SerializedObject`로 채움(런타임 API에 세터를 뚫지 않으려고). **이미 있는 에셋은 건드리지 않고, 관계도 새로 만든 것만 채운다**(사용자 수정 보존).

### 남은 데이터 작업 (사용자)
1. 위 메뉴 1회 실행.
2. 각 유닛 프리팹의 `Faction.Data`에 해당 SO 연결. **연결 전까지는 레거시 동작 유지**라 한 번에 다 바꾸지 않아도 됨. 단 관계는 **양쪽 다 연결돼야** 적용.
3. 필요하면 세력 추가/관계 수정(에셋 인스펙터).

### 후속 — 전투 성향: "적은 정해졌는데 도망을 안 감" (Play Mode 피드백)
관계 시스템만으로는 **적대 상대를 만났을 때의 반응**이 하나뿐이었다(무조건 교전). 도주 행동이 `NpcType.Villager` 트리에만 있어서, 마을사람 세력을 붙인 일반 유닛은 그냥 싸웠다.
- **`NpcFleeNode` → `FleeNode`로 승격**(NPC 전용 → 공용). `shouldFlee` 조건 델리게이트를 받아 "다치면 도주"를 같은 노드로 처리.
- 1차 구현은 성향을 `UnitData`에 넣었으나 **곧바로 되돌림** — 아래 참조.

### 후속 2 — 성향을 종족 데이터에서 개체(프리팹)로 이동 (설계 지적 반영)
사용자 지적: **`UnitData`는 종족 단위**(사람/고블린…)인데 거기에 전투 성향이 붙으면 같은 "사람"으로 마을사람·경비병·용병을 구분할 수 없다. 마을 세력이라고 전부 도망치는 것도 아니다(경비병·상인·용병은 싸우는 쪽).
- **`CombatBehavior` 컴포넌트 신설**(유닛 프리팹에 부착) — `Stance` / `FleeBloodRatio` / `FleeDistance` / `FleeDetectRange`. `UnitData`에서 성향 필드 전부 제거.
- **축 정리**: 종족(`UnitData`=스탯) / 세력(`FactionData`=누가 적인가) / **역할(`CombatBehavior`=적을 만나면 어떻게 하는가)**. 세 축이 독립이라 "고블린 종족 + 몬스터 세력 + 도주 성향(약한 고블린)" 같은 조합도 자유롭다.
- **`UnitBrain.AddCombatBranch(root, fallback, fleeRange)`** — 성향 분기 조립을 한 곳으로 모으고 적/경비/주민/**상점 상인** 트리가 공유. 컴포넌트가 없을 때의 기본값만 역할별로 다르다(일반·경비 = Fight, 주민·상인 = Flee).
- **상점 상인**도 이제 성향 분기를 갖는다(이전엔 공격받아도 Idle) — 기본 도주, `CombatBehavior`로 용병 상인 구성 가능.
- 기존 프리팹은 컴포넌트를 안 붙이면 이전과 동일하게 동작.

### 후속 4 — 유휴 배회: 할 일 없는 비플레이어 유닛이 제자리에 서 있던 것
적 유닛은 `Detect+Fight → Idle`이라 타겟이 없으면 **스폰 자리에 얼어붙어** 있었다. 배회는 `NpcType.Villager` 트리에만 있었음.
- **`NpcWanderNode` → `WanderNode` 승격**(공용) + `pauseMin/Max` 파라미터화 + **홈 지연 설정**: `UnitBlackboard.HomeSet`이 false면 처음 배회하는 순간의 위치를 홈으로 잡는다(적은 스폰 시 홈이 없었음 → 예전 방식이면 월드 원점 주변을 배회했을 것).
- **`WanderBehavior` 컴포넌트**(개체 단위, `CombatBehavior`와 같은 축): `Wander` / `Radius` / `PauseMin·Max`. 없으면 타입 기본값.
- **`UnitBrain.AddWanderBranch(root, defaultRadius, defaultOn)`** — 적/주민/경비/상인 트리 공유. 기본값: 적 = 배회(반경 12), 주민·경비 = 배회(`WanderRadius`), **상점 상인 = 제자리**(가게 지킴).
- 경비 트리는 `순찰 → 배회` 순 — **순찰 구역이 없으면 배회로 떨어진다**(이전엔 제자리).
- 침공 유닛 안전장치: `WanderNode`는 **이동 중이면 새 목적지를 주지 않는다** → 스폰 직후 `SetMoveTarget(집결지)`를 덮어쓰지 않고, 도착해 멈춘 자리를 홈으로 삼아 그 주변을 돈다.
- 플레이어 유닛(방랑자/하수인)은 대상 아님 — 작업 BT가 유휴를 채운다.

### 후속 5 — BT 시간 축 버그: 노드 안의 `Time.deltaTime` (배회가 "한 번 움직이고 멈춤"의 진짜 원인)
"배회가 한 번만 되고 그 다음이 없다"는 피드백에서 발견. **`UnitBrain`은 `tickInterval`(0.1초)마다 BT를 틱하는데, 노드들은 틱마다 `Time.deltaTime`(한 프레임 ≈ 0.016초)을 누적**하고 있었다 → 노드 안의 시간이 실제보다 **6배 이상 느리게** 흐른다(프레임레이트가 높을수록 더 느려짐).
- 배회 대기 2~6초 → 실제 **12~40초**. 그래서 한 번 움직인 뒤 한참을 서 있었다.
- 같은 버그를 공유하던 곳: **식사 시간**(`EatNode`, 6배 길어짐), **침대 회복**(혈액/혈액캡/부위 HP 6배 느림), **채굴·벌목 XP**(6배 적게), **순찰 대기**, **행상인 체류 시간**.
- 수정: **`UnitBlackboard.TickDelta`** 추가 — `UnitBrain.Update`가 틱할 때 실제 경과 시간(`_tickTimer`)을 넣어준다. 시간을 다루는 노드 7곳을 `Time.deltaTime` → `bb.TickDelta`로 교체.
- **밸런스 영향**: 이제 식사·회복·성장이 *설정된 수치대로* 동작한다 = 체감상 6배 빨라진다. 상수들(`EatTime`, `BloodHealRate`, XP 0.05 등)은 잘못된 시간 축에 맞춰 조정돼 있었을 수 있으므로 재조정이 필요할 수 있다.
- 배회 노드 추가 보강: 목적지를 **한 틱에 8번까지 재추첨**(던전에서 한 번만 뽑으면 대부분 공허에 떨어져 계속 실패), 전부 실패하면 `Failure`를 반환해 다음 분기로 넘김. `Mover` 없는 유닛 가드.

### 후속 7 — Play Mode 피드백 4건 (타겟 우선순위·이행 중 폴백·라벨)
1. **타겟 선정이 거리 기준이 아니었음** — `DetectNode`가 `OverlapSphere` 결과의 **첫 번째** 적을 잡아, 옆에 적을 두고 멀리 있는 상대를 패러 갔다. → **가장 가까운 후보**를 고르도록 교체. 반격 대상(중립이라 적대 스캔에 안 걸림)도 같은 거리 비교에 넣는다. 타겟 흔들림 방지로 **기존 타겟보다 1.5배 이상 가까울 때만 교체**하고, 새 후보가 없으면 기존 타겟을 유지(추격 중 놓치지 않게). `FleeNode`도 가장 가까운 위협 기준으로 변경.
2. **이행 중 폴백이 너무 공격적이었음** — 플레이어에 `FactionData`를 안 붙인 상태에서 마을사람(SO 있음)과 싸웠다. 기존 폴백은 "한쪽이라도 SO가 없으면 IsPlayer 비교 → 다르면 Hostile"이라, **중립이어야 할 상대와 전투**가 벌어졌다. → **둘 다 SO가 없을 때만** 레거시 2분법을 쓰고, **한쪽만 있는 이행 중 상태는 `Neutral`**(관계를 알 수 없으므로 싸우지 않음). 관계를 실제로 적용하려면 양쪽 다 SO를 붙여야 한다는 규칙은 그대로.
3. **UI 유형 라벨이 "적"으로 고정** — 비플레이어면 무조건 "적"이라 중립 마을사람도 `[적] (마을 사람)`으로 나왔다. → **우리 세력과의 관계 기준**(적/중립/우호)으로 표시. `Faction.Player`(플레이어 조작 세력 조회) static 추가 — `Faction`이 자기 자신을 정적 목록에 등록/해제.
4. **마을사람이 도망 안 감** — 원인은 그 유닛이 `NpcData`가 아니라 일반 `UnitData`였다는 것(라벨이 "주민"이 아니라 "적"으로 나온 게 단서). 일반 유닛의 기본 성향은 `Fight`이므로 **`CombatBehavior(Stance=Flee)`를 프리팹에 붙여야** 한다. 코드 수정 아님 — 데이터 작업.

### 후속 9 — 행동 설정을 SO(AI 프로필)로 통합
사용자 질문 "`CombatBehavior`와 `CombatHandler`가 나뉠 이유가 있나?" → 실행(명중·피해 계산)과 설정은 분리가 맞지만, **설정을 컴포넌트 2개(`CombatBehavior`/`WanderBehavior`)로 쪼갠 건 과했다**. 업계 관행에 맞춰 설정을 **SO 하나**로 합치기로 결정(사용자 선택).
- **`AiProfileData`(SO, `Create → DungeonColony → AiProfileData`)** 신설 — 전투(`Stance`/`FleeBloodRatio`/`FleeDistance`/`FleeDetectRange`) + 유휴(`Wander`/`WanderRadius`/`PauseMin·Max`). `CombatStance` enum도 여기로 이동.
- **`CombatBehavior`/`WanderBehavior` 컴포넌트 삭제.** 연결은 **`UnitBrain.aiProfile`** 필드 — `UnitBrain`은 모든 폰에 이미 있으므로 **새로 붙일 컴포넌트가 없다**. 프로필 하나를 여러 프리팹이 공유(겁쟁이 민간인 프로필 → 마을사람·아이·잡상인).
- 비우면 기존과 동일한 타입별 기본값. `CombatHandler`(전투 실행)는 그대로.
- **`Editor/AiProfileCreator.cs`** — `DungeonColony → Create Starter AI Profiles`로 4종 생성: 겁쟁이 민간인(도주, 감지 12) / 전투원 / 신중한 전투원(혈액 40% 아래 후퇴) / 보초(교전+제자리).
- SO 승격 시점 판단: 프로필이 한둘일 때 SO부터 만들면 파일만 늘지만, 이 프로젝트는 이미 `UnitData`/`FactionData`로 SO 패턴을 쓰고 역할 반복(마을사람 계열 여럿)이 예상돼 지금이 적기.

### 후속 10 — 플레이어 유닛은 성향을 런타임에 전환 가능하게
"플레이어에겐 적용 안 되는 경우도 있으면 좋겠다 / NPC와 다르게 유동적으로" 요청. NPC·적은 프로필 에셋으로 고정 운용하지만, 플레이어 유닛은 상황에 따라 바꿔야 한다.
- **`UnitBrain.SetStanceOverride/ClearStanceOverride/EffectiveStance/ShouldFleeNow`** — 우선순위 **런타임 오버라이드 > AI 프로필 > 역할 기본값**. 프로필 에셋은 건드리지 않고 그 유닛만 바꾼다.
- **성향을 매 틱 읽도록 BT 구조 변경**: 조립 시점에 `Flee`면 교전 노드를 빼던 방식 → 항상 `FleeNode(조건: ShouldFleeNow)` + `ConditionNode(EffectiveStance != Flee)`로 감싼 교전 시퀀스. **BT 재조립 없이** 런타임 전환이 즉시 반영된다.
- **플레이어 트리에 도주 분기 추가**(`PlayerFleeNode`) — 방랑자는 소집 분기 뒤, 하수인은 맨 앞. 기본 성향이 `Fight`라 **평소엔 즉시 실패**해 기존 동작과 동일하고, 프로필/오버라이드를 줄 때만 켜진다. **소집(Draft) 중에는 도주하지 않는다**(플레이어 명령 우선).
- UI는 아직 없음 — 코드 API만. 스탯 패널이나 폰 로스터에 성향 토글을 붙이면 인게임 전환 가능.

### 후속 8 — 도주가 중간에 멈추는 문제: 히스테리시스 + 부채꼴 지점 탐색
"도망은 가는데 어느 지점에서 멈춘다 / 고양이 본 생쥐처럼 계속 달아났으면" 피드백. 원인 두 가지를 함께 처리.
- **감지 경계에서의 딸꾹질**: 위협이 `FleeDetectRange` 밖으로 나가는 순간 도주가 `Failure` → 배회/대기로 내려갔다가, 상대가 다시 들어오면 재도주. 경계에서 멈춘 것처럼 보인다. → **`ReleaseMult = 2.5`**: 도주를 시작하면 감지 범위의 2.5배까지 위협을 추적한다. 쫓아오는 한 계속 달린다.
- **막다른 곳**: 도주 지점이 벽·낭떠러지(공허)면 `PawnMover`가 멈춰 세우고, 매 틱 같은 방향을 다시 찍어 그대로 굳었다. → **`TryPickFleeSpot`**: 위협 반대 방향에서 좌우로 부채꼴(±25°/50°/80°/110°)을 돌며 설 수 있는 지점을 찾고, 다 막히면 거리를 0.6배·0.3배로 줄여 재시도. 완전히 몰리면 이동 명령 없이 버틴다.
- **재계획 주기 0.3초**(`RepathInterval`) + **멈춰 서면 즉시 재탐색** — 매 틱 목적지를 새로 주면 길찾기가 요동치고, 안 주면 막힌 채 굳는다.
- 위협이 사라지면 `StopMovement`로 도주 종료(관성으로 계속 달리지 않게). 시체·기절한 적은 위협에서 제외.

## 2026-07-27 (3) — 건물이 바닥에 파묻히는 문제: 표면 높이(바닥 윗면) + 렌더러 바닥면 스냅

배치한 건물이 `y=0`에 놓여 바닥/지면에 박힌 채로 건설되던 문제. 원인은 두 겹이었다.
1. **바닥 두께 무시** — `MapManager._floored`가 `HashSet`이라 바닥의 *높이*를 몰랐고, `SampleGroundHeight`는 공허 던전 씬(지형 없음·`groundMask=0`)에서 항상 0을 반환 → 슬래브(두께 0.05) 안쪽 높이에 건물이 놓임.
2. **프리팹 피벗** — 배치 Y는 "피벗을 놓을 높이"라, 피벗이 메시 중앙인 프리팹(큐브류)은 절반이 표면 아래로 들어감. 이쪽이 "박힌다"의 주원인.

### 수정 1 — 바닥이 자기 윗면 높이를 등록
- `MapManager._floored`: `HashSet<Vector2Int>` → **`Dictionary<Vector2Int, float>`**(타일 → 바닥 윗면 월드 Y). 겹치면 더 높은 면 채택.
- `RegisterFloor(tile, surfaceY = 0f)` / **`TryGetFloorSurface`** / **`SurfaceHeight(tile)`**(바닥 있으면 그 윗면, 없으면 기존 지형 샘플) 추가. `TileToGround`가 `SurfaceHeight` 기반으로 변경 → 그리드 배치·미리보기·`CoreRelocator`가 자동으로 바닥 윗면을 씀.
- `Floor`: `ComputeSurfaceY()`(렌더러 바운드 상단, 없으면 피벗)를 등록. 배치 후 위치 보정에 대응하는 **`Refresh()`** 공개(등록 좌표·높이 재계산).

### 수정 2 — 렌더러 바닥면을 표면에 스냅 (피벗 무관)
- **`BuildModeManager.SnapOnSurface(go, surfaceY)`** — 자식 `MeshRenderer`/`SkinnedMeshRenderer` 바운드를 합쳐 `bounds.min.y`가 표면에 닿도록 Y 보정. 파티클/트레일 렌더러는 바운드가 형상과 무관해 제외, 렌더러가 없으면 보정하지 않음(근거 없음).
- 적용: 즉시 배치(`Place`), 바닥 배치(스냅 후 `Floor.Refresh`로 윗면 재등록), **고스트 미리보기**(`ShowGhost` — 미리보기와 결과가 같은 높이), 2단계 건설(`BuildingBlueprint`의 청사진 시각 + `Complete`의 실제 스폰).
- 자유 배치: `OnSurface(p)`로 **XZ는 자유, Y만 바닥 윗면**으로 교체(레이가 벽·건물에 맞아도 슬래브 위에 얹힘).
- `GridRenderer` 오버레이(점유/미리보기)도 `SurfaceHeight` 기준으로 변경 — 바닥 위 타일에서 슬래브 밑에 깔리거나 z-fighting 나던 것 해소.

### 후속 — 일부러 띄워둔 코어가 배치/이전 시 바닥에 박히던 문제 (Play Mode 피드백)
메인 핵은 씬에서 의도적으로 띄워둔 오브젝트인데 **이전하면 표면 높이로 눌려 박혔고**, 서브코어는 프리팹 루트에 `localPosition.y = 2`로 부양을 저작해뒀지만 `Instantiate(prefab, pos, rot)`가 그 Y를 덮어써 버려 애초에 안 떠 있었다(스냅 도입 이전부터의 동작).
- **`BuildModeManager.AuthoredHover(prefab)`** — 프리팹 루트 `localPosition.y`(양수만)를 "저작된 부양 높이"로 읽는다.
- **`SpawnOnSurface(prefab, surfacePos, rot)`** — 부양 높이가 있으면 그만큼 띄워 스폰(바닥 스냅 안 함), 없으면 기존대로 렌더러 바닥면 스냅. 즉시 배치·바닥·청사진 완성이 모두 이 경로를 씀.
- **`SnapOnSurface`는 이제 "올리기만"** 한다 — 메시가 피벗보다 위에 저작된 프리팹을 끌어내리지 않도록(dy > 0일 때만 이동).
- **고스트**: 모델을 컨테이너 아래 `localPosition.y = hover`로 붙이고, 부양 프리팹이면 스냅 생략 → 미리보기 높이 = 실제 배치 높이. 청사진 시각도 동일 규칙.
- **`DungeonCore._hoverOffset`**: `Start`에서 `현재 Y − 표면 높이`를 저작 부양 높이로 캡처 → `RelocateTo`가 `목적지 표면 + 부양 높이`에 놓는다. 씬마다 다른 부양을 코드 상수 없이 유지.
- 서브코어 영역 판정은 XZ 거리라(`IsWithinRangeWorld`) 부양이 범위에 영향을 주지 않음. 확인함.

### 범위/한계
- 부양 높이의 근거는 **프리팹 루트 Y**다. 자식 메시만 올려둔 프리팹은 "메시가 피벗 위" 케이스라 스냅이 올리지 않을 뿐(=그대로 유지), 별도 데이터 필드는 두지 않았다.
- 유닛 발높이는 손대지 않음(길찾기는 Y=0 평면 기준). 바닥 두께(0.05)만큼 건물이 유닛보다 높아지지만 시각적으로 무의미.
- 타일당 단일 높이 — **경사 바닥/다층 바닥은 미지원**(같은 타일에 바닥이 겹치면 높은 쪽 하나만).

### 검증 필요 (Play Mode)
0. (후속) 서브코어 배치 → 프리팹에 저작한 높이(y=2)만큼 **떠서** 놓이는지. 핵 이전 → 메인 핵이 이전과 같은 높이로 **뜬 채** 옮겨지는지(박힘 없음).
1. 던전 바닥 위에 건물 배치 → 바닥 **위에 얹혀** 보이는지(파묻힘 없음). 피벗이 중앙인 프리팹도 마찬가지인지.
2. 고스트 미리보기 높이 = 실제 배치 높이인지(배치 순간 튀지 않는지).
3. 2단계 건설(청사진)도 동일 — 청사진 시각과 완성 건물이 같은 높이인지.
4. 바닥 깔기 → 슬래브가 지면에 붙는지, 그 위 건물이 슬래브 윗면에 앉는지.
5. 회귀: 바닥 없는 지형 맵(필드 씬)에서 기존처럼 지면에 배치되는지.
6. 그리드 오버레이(빨강 점유/초록 미리보기)가 바닥 위에 보이는지.

## 2026-07-27 (2) — 휴면 건물 = 전면 사용 불가로 확정 + 새던 경로 4곳 차단

설계 미결 "비활성 건물의 상호작용 정의"를 **휴면 건물은 당연히 사용 불가**로 확정(사용자 결정). 기존 구현은 `FarmPlot`/`CraftingTable`/`WaterSource` `enabled=false` + `Storage.IsActive`만 막고 있어 실제로는 네 군데가 새고 있었음.

### 차단 1 — 침대 (자동 휴면)
`Bed`는 인스펙터 `suspendOnDormant` 목록에 넣어야만 꺼졌음(사실상 미적용) → `BuildingDormancy.GatherTargets`에 **자동 포함**. `Bed.OnDisable`이 정적 목록에서 자신을 빼므로 `FindAssigned`/`TryOccupy` 대상에서 제외 = 휴면 침대에서 잠들 수 없음. `AssignedUnit` 배정 정보는 남아 영역 복구 시 그대로 복원.

### 차단 2 — 큐에 남아 있던 일감 (대기, 취소 아님)
휴면 전에 등록된 일감(제작 주문·연료·연구·파종/급수/수확)은 그대로 배정 가능했음.
- **`JobBase.SetSite(component)` / `IsSiteUsable`** — 작업이 매달린 건물의 `BuildingDormancy`를 생성 시 캐시(O(1) 판정).
- **`JobManager.RequestJobInternal`**에 `IsSiteUsable` 게이트 추가 → 휴면 건물 일감은 **큐에 남은 채 배정 보류**, 영역 복구 시 자동 재개. 재료 부족 대기(`IsReady`)와 같은 정책이라 주문이 사라지지 않음.
- 적용: `CraftJob`/`FuelJob`/`ResearchJob`(작업대·연구대), `SeedJob`/`WaterJob`/`FarmHarvestJob`(농지).
- **운반 계열(`HaulJob`/`GroundHaulJob`)은 제외** — 창고는 "작업 현장"이 아니라 목적지고, 이미 `Storage.IsActive`로 탐색에서 빠짐. 여기에 게이트를 걸면 목적지 창고가 영영 안 돌아올 때 운반이 영구 정지함.

### 차단 3 — 클릭해서 패널 열기
휴면 건물도 클릭하면 패널이 열려 조작 가능했음 → `SelectionManager`의 `IWorldClickable` 라우팅에서 **휴면이면 패널을 열지 않음**(로그만). 클릭 경로가 일원화돼 있어 창고/침대/농지/작업대/연구대/순찰구역 전부 한 곳에서 차단됨.

07-11 백로그 "기절 영구" 처리. 기절은 걸리기만 하고 해제 코드가 없었음 + 출혈 페이싱(기존 1~5/s, 20~100초 사망)이 너무 빨랐음.

### 설계 (켄시식 상태 기반)
- **기상 조건** (`BodyPartSystem.UpdateKnockOutRecovery`): 최소 기절 시간(`minKnockOutSeconds` 20s) 경과 + 코어 부위(머리/가슴/복부) 전부 HP > 0 + 혈액 ≥ `wakeBloodRatio`(25%). BloodCap이 기준 밑까지 깎였으면 캡까지 찼을 때 기상 허용(기절 중엔 침대 못 가는 교착 방지). `OnRecovered` static event 추가.
- **자연 지혈**: 부상 후 `clotSeconds`(30s)에 걸쳐 출혈 선형 감쇠, 재피격 시 리셋(`BodyPart.LastWoundTime`). 단일 부상은 출혈만으론 안 죽고 연타당할 때만 위험. BleedRate도 하향: 머리 3→0.5 / 가슴 5→0.8 / 복부 2→0.4 / 팔다리 1→0.2.
- **자연 회복** (`UpdateRegen`): 혈액 0.2/s(BloodCap까지) + 부위 HP 0.25/s(파괴 부위 제외 — 파괴는 영구). 부위 회복이 기상 조건과 절뚝임 해제를 성립시킴.
- **기절 부수효과 차단** (`KnockOut`): BT 정지로 못 끄던 `CombatHandler.ExitCombat()` + `PawnMover.StopMovement()` 직접 호출 — 쓰러진 채 매 프레임 공격하던 구멍 해소.
- **침대 연동** (`RestNode`): 부위 HP 회복 추가(`PartHealRate` 1/s, 자연 회복에 얹힘), 휴식 트리거/퇴장 조건에 `HasRecoverableDisabledPart`(파괴 제외 기능상실 부위) 반영.
- **피격 혈액 손실 (2차 — 켄시 축 완성)**: 베기만 혈액을 깎던 것 → **모든 피해가 혈액을 깎음**(베기 0.5× / 둔기 0.1× / 그 외 0.25×). 혈액 20% 미만 → **과다출혈 기절**(강인함 무관, `CheckBloodState` 공통 판정 — 피격/출혈 양쪽). 기상 기준(25%)이 기절 임계(20%)보다 높아 기상 직후 재기절 없음.
- **기절 재판정 + 확정 기절**: 이미 기능 상실한 코어 부위(머리/가슴/복부)를 또 맞으면 `TryKnockOut` 재굴림(기존엔 0을 처음 넘는 순간 한 번만 판정). 코어 부위 HP가 `coreKoDepth`(-10) 이하로 깊어지면 **무조건 기절** — 굴림은 0 근처에서 버티는 용도로만. 강인함 저항은 최대 90% 캡(스탯 0~130이라 100+에서 기절/비틀거림 완전 면역이던 것 수정).
- 수치는 전부 `BodyPartSystem` 인스펙터 SerializeField — Play Mode 튜닝 가능.

### 3차 — Play Mode 테스트 피드백 반영 ("기절을 못 봄" 원인 3중)
- **혈액 음수 허용 + 사망 분리**: 강한 타격이 기절 임계(20%)를 건너뛰고 혈액 0 → 즉사하던 것 수정. 켄시식 — 혈액은 음수로 내려가며 `deathBloodRatio`(-30%)에 닿아야 사망. 기절(20% 미만)→빈사(음수)→사망(-30%) 구간이 생김.
- **기절 유닛 타겟팅 제외** (`BTTargetUtil.IsAttackable`): 적이 쓰러진 유닛을 계속 때려 KO가 수 초 만에 사망으로 이어지던 것 → 기절 유닛은 자동 타겟에서 제외(다른 대상으로 전환). KO가 사형선고가 아니라 회복 가능한 상태가 됨. 부작용: 플레이어 지정 공격도 기절 대상은 못 잡음(확인 사항).
- **눕는 포즈**: 기절 시 Z축 90도 회전, 기상 시 복구 — 기절이 눈에 보이게 됨(CharacterController 캡슐은 회전 무시라 충돌 무영향). 애니메이션 도입 전 임시.
- **`UnitHPUI` MissingReferenceException**: 선택 중이던 유닛이 사망(Destroy)하면 파괴된 `PawnMover` 참조로 매 프레임 예외 → null 가드 + 패널 닫기.

### 검증 필요 (Play Mode)
1. 유닛 기절시키기(코어 부위 기능상실 or 혈액 20% 미만) → 20초+ 후 조건 회복되면 스스로 기상, 기상 후 BT 정상 재개(작업/전투 복귀)
2. 기절 중 공격 안 함 / 이동 정지
3. 출혈: 한 대 크게 맞고 방치 → 30초쯤 뒤 출혈 멎고 혈액 서서히 회복
4. 다리 기능상실 절뚝임 → 시간 지나면(또는 침대) 정상 보행 복귀
5. 팔다리 파괴(-100)는 회복 안 됨(영구) + 그 상태로 침대에서 나옴(교착 없음)
6. 지속 전투에서 혈액이 매 타격 감소 → 20% 밑에서 쓰러짐(사망 아님), 죽는 건 혈액 0 도달 시만

## 2026-06-07 — 지형 샘플 회귀 수정 + 건물 철거(데몰리시) 기능

### 1. step 2 회귀 수정 (빨간 미리보기 + 건물 바닥 박힘)
- 평지(y=0) 씬에서 `SampleGroundHeight`가 `groundMask=Everything(~0)`로 아래를 레이캐스트 → 건물/코어/유닛 콜라이더를 지면으로 오인 → 코너 높이 들쭉날쭉(평탄도 빨강) + 배치 Y 엉뚱(박힘).
